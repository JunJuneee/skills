## 3. PR 리뷰 루프 — comment 기반

**문제가 없을 때까지 리뷰를 반복한다.** 한 번의 리뷰로 끝내지 않는다.

### 흐름

```
qwen4-max-preview로 구현 완료
  ↓
PR 생성 (draft 또는 regular)
  ↓
deepseek-v4-pro-0813에게 리뷰 요청
  ↓
리뷰 결과를 PR comment로 게시
  ├─ 지적 있음 → qwen4-max-preview로 수정 → push → 재리뷰 요청 (반복)
  └─ 지적 없음 → "작업 완료" comment 게시 → PR 병합
```

### 규칙

1. **리뷰 요청**: PR이 생성되면 deepseek-v4-pro-0813에게 리뷰를 요청한다. 리뷰어는 구현에 참여하지 않은 별도 세션/에이전트여야 한다.
2. **comment 게시**: 리뷰 결과(지적사항, 승인, 반려)는 반드시 **PR comment**로 남긴다. 로컬 보고나 Linear 요약만으로 대체하지 않는다.
3. **수정 후 재리뷰**: 지적사항을 수정하고 push한 뒤, 반드시 deepseek-v4-pro-0813에게 **재리뷰**를 요청한다. 이전 리뷰의 승인으로 새 변경을 통과시키지 않는다.
4. **완료 comment**: 모든 지적이 해소되고 리뷰어가 승인하면, PR에 **"작업 완료"** comment를 남긴다.
5. **병합**: 완료 comment 게시 후 PR을 병합한다. 병합 전 최신 head·필수 체크·저장소 정책을 확인한다.
6. **반복 제한 없음**: 문제가 없을 때까지 반복한다. 라운드 수를 채웠다는 이유로 끝내지 않는다.

### comment 형식 예시

```markdown
## 리뷰 결과 (deepseek-v4-pro-0813)

**대상 SHA**: abc1234
**결론**: 변경 요청

### 지적사항
1. [파일:라인] 설명...
2. [파일:라인] 설명...

---
수정 후 재리뷰를 요청합니다.
```

```markdown
## 작업 완료

모든 리뷰 지적사항이 해소되었습니다.
- 리뷰어: deepseek-v4-pro-0813
- 최종 SHA: def5678
- 리뷰 라운드: 3
- 결론: 승인

PR을 병합합니다.
```

## 4. 사용자 확인 대체 — 이중 critique 자율 판단

야간 작업 중 **사용자에게 확인·질문해야 할 상황**(방향 선택, 모호한 요구사항, 설계 결정, 범위 조정 등)이 생기면, **사용자를 기다리지 않고** 이중 critique로 판단해서 진행한다. 야간에 사용자는 자고 있으므로, 엄청 크리티컬한 경우가 아니면 작업을 멈추지 않는다.

### 흐름

```
사용자 확인이 필요한 상황 발생
  ↓
두 검토자에게 critique 요청 (병렬)
  ├─ deepseek-v4-pro-0813 — 리뷰 모델, 별도 세션
  └─ qwen4-max-preview — 신규 세션 (구현에 참여하지 않은 독립 컨텍스트)
  ↓
critique 종합
  ├─ 크리티컬 아님 → 수정할 것 수정 → 작업 계속 진행 (결정 근거 기록)
  └─ 크리티컬 → agent-running 제거 + needs-confirm 부착 → 해당 이슈 보류 (종료)
```

### 규칙

1. **질문 대신 critique**: 사용자에게 질문을 던지고 대기하는 대신, 결정이 필요한 사항(쟁점·선택지·추천안·영향 범위)을 정리해 두 검토자에게 critique를 요청한다.
2. **둘 다에게 요청**: deepseek-v4-pro-0813과 **신규 세션의** qwen4-max-preview 둘 다에게 요청한다. qwen4-max-preview critique는 구현 세션과 분리된 새 에이전트/세션이어야 한다 — 확증 편향을 막기 위해서다.
3. **수정 후 진행**: critique에서 지적된 것은 수정하고, 종합한 판단으로 작업을 계속 진행한다. 의견이 갈려도 멈추지 않는다 — 더 안전한 쪽 또는 다수 의견을 채택하고 근거를 기록한다.
4. **기록**: 결정 내용과 critique 요약은 **PR comment**로 남긴다(PR이 아직 없으면 Linear 이슈 comment). Linear 이슈 작업이면 결정 완료 시 `agent-decided` 라벨을 부착한다.
5. **크리티컬만 보류**: 아래 크리티컬 기준에 해당하는 경우에만 작업을 멈추고 사용자 확인을 기다린다. 나머지는 전부 진행한다.

### 크리티컬 기준 — 이때만 보류

| 보류 (사용자 확인 대기) | 진행 (이중 critique 후) |
|------|------|
| 비가역적 파괴 (데이터 삭제, force-push, 원격 브랜치 대량 삭제) | 구현 방향·설계 선택 |
| 보안·자격증명·결제/비용 관련 결정 | 모호한 요구사항 해석 |
| PR 외 외부 공유 상태 변경 (Slack 메시지·공개 게시 등) | 리팩토링 범위·우선순위 조정 |
| 두 검토자 모두 고위험 판정, 안전한 대안 없음 | 테스트·문서·라벨 정리 |
| — | 한쪽만 지적 (수정 후 진행) |

- 보류 시: Linear 이슈에서 `agent-running` 라벨을 **제거**하고 `needs-confirm`을 부착한 뒤, 쟁점을 기록하고 **해당 이슈만** 중단한다. 다른 이슈 작업은 계속 진행한다. (`agent-hold`는 사람이 보류를 지시할 때 쓰는 라벨이므로 자율 보류에는 부착하지 않는다.)
- 배포·프로덕션 영향은 보류 대상이 아니라 **§5 절대 금지** 대상이다 — 사용자 확인으로도 야간 배포는 허용되지 않는다.
- 이 규칙은 작업 대상 레포에 오너 게이트 규약(CLAUDE.md 등)이 있으면 그 규약을 덮어쓰지 않는다. 오너 게이트가 금지하는 사항은 자율 판단 대상이 아니다.

## 5. 배포 금지 — 절대 규칙

**중국 모델을 사용하는 야간 작업에서 배포는 절대 수행하지 않는다.**

| 허용 | 금지 |
|------|------|

| 테스트 작성 및 실행 | staging / production 전송 |
| PR 생성 · 리뷰 · 병합 | Docker 빌드 · 이미지 푸시 |

배포가 필요하면 **주간 시간대에 전환**하거나 사용자가 명시적으로 "배포 승인"이라고 지시한 경우에만 진행한다. 야간 자동 실행에서는 어떤 경우에도 배포하지 않는다.
