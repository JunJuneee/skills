# 모델과 위임 계약

## 새 작업의 메인 루프 시험

- 새 이슈·PR에만 `main-loop-v1`을 적용한다. 같은 작업의 후속 요청·재개는 기존 계약을 유지하며, 기존 세션의 모델·소유·역할을 소급 변경하지 않는다.
- 조율자가 아래 구현 모델·추론 계약을 충족하면 계획·관련 코드 탐색·구현·리뷰 수정을 같은 세션에서 수행한다. 충족하지 않으면 계약에 맞는 구현 세션 한 명에게 계획부터 수정을 이어 맡기고 조율자는 중복 기술 탐색·계획 작성을 피한다. 통합을 위해 구현 모델·추론을 낮추지 않는다. 구현 모델은 아래 위험도 등급·[명세형 일반 작업](#명세형-일반-작업) 규칙·[야간 구성](#야간-구성)이 정한다(2026-11-16 사용자 지시). 이 규칙이 [Sonnet medium 3건 시험](../../agent-workflow/references/sonnet-medium-implementation-pilot.md)의 슬롯 상한보다 우선하며, 시험 장부는 더 이상 구현 모델 선택을 제한하지 않는다.
- 분류·요약·단순 전달·진행 감시 전용 에이전트는 기본으로 만들지 않는다. 필요한 스킬·원본 일부만 읽고 긴 로그는 파일과 관련 부분을 참조한다. 단일 문맥에 모든 원문을 쌓는 방식으로 바꾸지 않는다. 독립 컴포넌트·문맥 과부하·도구나 지침 충돌에 따른 반복 실패는 근거를 기록하고 분리할 수 있다.
- 반대 계열 계획 critique(기본 3인, [명세형 일반 작업](#명세형-일반-작업)은 1인), 별도 테스트 작성자, 또 다른 실행 검증자, 독립 Qwen 최종 리뷰를 유지한다. 구현을 맡은 조율자를 독립 검증자·최종 리뷰어로 세지 않는다. 외부 쓰기 단일 담당, hold·소유·최신 SHA·실제 모델 확인과 승인 범위도 유지한다.
- 새 계약에 시험 표식·시작/완료 시각·종류/위험도·주 실행 및 모든 하위 역할의 세션 ID를 남긴다. 기존 완료 증거에 실패·재시도·미검증·재작업을 연결한다. 별도 모델 벤치마크·감시 에이전트·주기 조회는 추가하지 않고 기존 로그로 관찰한다.
- 첫 완료 5건에서 같은 종류·위험도·정확한 모델/추론의 이전 작업과 작업당 사용량·완료 시간·재작업을 비교한다. 입력·캐시 입력·출력·추론 출력을 구분하고 캐시는 입력, 추론은 출력에 포함되므로 중복 합산하지 않는다. 모든 역할과 실패·재시도를 포함하되 미수집 공급사는 미확인으로 표시한다. 총량만으로 절감률을 단정하지 않는다. 새 검증 누락·결함·재작업 증가가 확인되면 해당 역할 분리를 복원하고 원인을 확인한다.

## 모델 선택과 반대 계열 critique

Traycer agent selection guide를 읽고 `traycer_list_harness_models`로 실제 실행 호스트·작업 디렉터리의 지원 모델·추론 수준을 확인한다. 명시적인 사용자 지시를 우선하고, 역할별 모델 식별자는 최초 배정 시 사용 가능한 같은 계열 최신 모델로 해석해 정확한 식별자를 기록한다.

새로 배정하는 Claude Opus 역할은 **Opus 5.5 필수**다. 호스트 모델 목록을 확인하고 `opus` 별칭은 실제 Opus 5.5로 실행되는 경우에만 사용한다. 결과 수락이나 리뷰 게시 전에 기여한 assistant 턴의 transcript에서 실제 provider·model을 확인하고 정확한 모델과 세션 ID를 기록한다. 설정값·별칭·목록 표기만으로 실제 실행을 증명하지 않는다. 이전 버전이 실행되거나 5.5의 사용 가능 여부 또는 실제 모델을 확인할 수 없으면 해당 역할을 hold하고 보고한다. 자동 하향하거나 그 결과를 수락하지 않는다. 진행 중인 작업 계약은 사용자가 달리 지시하지 않으면 유지한다.

**계열의 기준은 실제 구현 하네스다.** 사용자 지정과 진행 중인 기존 작업 계약을 우선한다. 새 작업은 주간에 SaladLab 저장소는 Claude Sonnet, JAY 프로젝트는 Codex Terra를 기본으로 하고 어려운 작업은 각각 Opus, Sol로 상향한다. 야간 일반 작업은 아래 야간 구성을 따른다. 프로젝트가 겹치거나 불명확하면 확인한다. 조율자가 Codex여도 Claude 구현을 지정했으면 Codex가 critique한다. 반대로 Claude 조율자가 Codex 구현을 지정했으면 Claude가 critique한다. 테스트 작성자나 최종 PR 리뷰어 모델로 반대 계열을 계산하지 않는다.

한 이슈마다 `implementation_harness`, `critique_harness`, 계획 작성자·조율자·구현자·검토자의 실제 모델과 세션 ID를 작업 계약에 고정한다. 실행 계획의 기술 내용은 구현 계열의 세션이 작성·보완한다. 조율자 계열이 달라도 계획 작성자와 critique는 반대 계열이 된다. 중간에 구현 계열을 명시적으로 바꾸면 새 구현 계열에서 계획을 보완하고 그 반대 계열이 작업 계약의 인원으로 critique를 다시 수행하며 테스트·검증 배정도 새 구현 계열에 맞춘다. 이전 계획 critique 결과는 이력으로 보존하되 새 조합의 critique로 세지 않는다. 장애 때문에 구현 계열을 몰래 바꾸지 않는다.

| 역할 | Codex 구현 | Claude 구현 | 경계 |
| --- | --- | --- | --- |
| 조율·외부 쓰기 | 현재 작업 소유 조율자 (기본 Codex Terra · high) | 현재 작업 소유 조율자 (기본 Codex Terra · high) | Codex/Claude 중 단일 담당, 모델 계열은 구현자와 달라도 됨. 위험도는 조율자가 판정하므로 착수 전 고정 모델은 일반 등급 기준이다 |
| 실행 계획 구체화·구현·리뷰 지적 수정 | 일반 Codex Terra · high / 고위험 Sol · high/xhigh | 일반 Claude Sonnet(5.5) · high / 단순 버그 수정 Haiku(5.5) · high / 고위험 Opus · xhigh | 계획 후 critique 결과 반영·로컬 구현·커밋, 외부 쓰기는 조율자 담당 |
| TC·테스트 코드 작성 | 별도 Codex Luna · high | 별도 Claude Sonnet · medium | 구현자와 다른 세션. 기본 1명이며 서로 겹치지 않는 영역(예: UI·E2E)이 실제로 있을 때만 나눈다 |
| 독립 테스트 실행·검증 | 또 다른 Codex Luna · high | 또 다른 Claude Sonnet · medium | 최종 코드에서 실제 검사·증거 확인 |
| 복잡한 테스트·원인 분석 | Codex Sol · high/xhigh | Claude Opus · xhigh | 어려운 작업을 상향 |

**추론 수준은 위험도 등급이 정한다.** `xhigh`·`max`는 고위험 작업과 복잡한 원인 분석 상향에서만 쓰고 일반 작업의 기본값으로 쓰지 않는다. 위험도는 §3의 판정을 따르며 불명확하고 피해가 클 수 있으면 고위험으로 본다. 일반 등급으로 시작한 작업이 중간에 고위험으로 재분류되면 이후 구현·리뷰를 고위험 수준으로 올리고 계획 critique는 §3의 재분류 절차를 따른다. 야간(23:00~09:00 KST)에는 아래 [야간 구성](#야간-구성)을 따른다.

### 명세형 일반 작업

Linear 이슈가 목표·변경 범위·완료 기준을 이미 담고 있고(사용자가 쓴 명세), 영향 범위가 한정된 비고위험 작업이다. 모델은 계획을 처음부터 세우는 대신 명세를 현재 코드에 맞춰 구체화(대상 파일·테스트)하고 구현한다.

- 구현·구체화·수정은 같은 세션이 맡는다. Claude 구현은 Sonnet(5.5) · high, Codex 구현은 Terra · high다. 설계·주 구현은 프로젝트에 따라 Sonnet 또는 Terra가 맡으며 어려운 작업·고위험은 각각 Opus 또는 Sol로 상향한다.
- 계획 critique는 반대 계열 **1명**이다(Claude 구현 → Codex Terra · high, Codex 구현 → Claude Sonnet · high). 아래 일반 작업의 3개 관점(요구사항·설계·검증)을 한 명이 모두 다루며 "이슈 명세와 실제 코드가 어긋나는 곳, 빠진 상태, 검증 불가능한 완료 기준"을 우선 본다.
- 구체화한 계획이 이슈의 범위나 완료 기준을 실질적으로 바꾸거나 위험도가 고위험으로 바뀌면 명세형이 아니다. 3명 체계로 바뀐 계획을 다시 검토받는다.
- **단순 버그 수정:** 원인이 이미 특정돼 있고 변경이 단일 파일의 국소 수정이며 기존 테스트나 작은 회귀 테스트로 검증되는 비고위험 수정은 Haiku(5.5) · high가 구현한다. 한 번의 테스트 사이클에서 실패하거나 범위가 넓어지면 Sonnet으로 올린다.
- **Haiku의 다른 역할:** 여러 파일에 걸친 읽기 전용 탐색, 문서·로그 요약, 명확성·단순성 점검(critique). 탐색은 구현자가 직접 하는 것이 기본이며, 넓은 탐색만 별도 Haiku 세션이 짧은 결과 파일로 남긴다. 코드 승인·어려운 결함 판정·최종 리뷰·독립 실행 검증은 Haiku에 맡기지 않는다.
- **상향:** 같은 완료 기준의 테스트가 반복 실패하거나 리뷰가 2라운드 이상 이어지면 구현을 Claude는 Opus, Codex는 Sol로 올린다. 상향한 사실·사유는 작업 기록에 남기고 사용량은 해당 작업에 포함한다.
- 별도 테스트 작성자·독립 실행 검증·최종 리뷰는 그대로다.
- 모델 이름은 `sonnet`·`haiku` 별칭으로 지정해도 되며, 실제 실행 모델(5.5 여부)은 transcript의 provider·model로 확인해 기록한다.

### 일반 작업: 계획 critique 3인의 역할

| 관점 | Codex 구현 → Claude critique | Claude 구현 → Codex critique |
| --- | --- | --- |
| 요구사항·범위·완료 기준·명확성·모순·빠진 상태·복잡성 | Sonnet · high | Terra · high |
| 기술 설계·실패·의존성·운영·권한·데이터·복구 | Sonnet · medium | Terra · high |
| 재현·테스트·회귀·관측 가능성 | Haiku · 지원되는 기본값 | Luna · high |

각 검토자는 배정된 관점 전체를 실제 코드 및 계획에 대조한다. 검토 범위가 한 사람에게 지나치게 넓거나 고위험이 발견되면 인원을 추가하고 판단 근거를 기록한다. 최종 코드 리뷰·독립 실행 검증은 별도다.

### 고위험 작업: 계획 critique 3인의 역할 (시험 적용)

3명이 각각 독립적으로 같은 계획 버전을 검토하며 기존 5개 관점을 다음과 같이 모두 다룬다. 각 행은 독립 세션 한 명이다.

| 담당 | 관점 | Codex 구현 → Claude critique | Claude 구현 → Codex critique |
| --- | --- | --- | --- |
| 1 | 요구사항·범위·완료 기준과 명확성·모순·빠진 상태·복잡성 | Opus · xhigh | Terra · xhigh |
| 2 | 기술 설계·실패 처리·의존성과 운영·권한·데이터·재시작·되돌림 | Opus · xhigh | Terra · xhigh |
| 3 | 재현·테스트·회귀·관측 가능성 | Sonnet · medium | Sol · high |

검토자는 배정된 관점 전체를 실제 코드와 계획에 대조하고 관점별 발견·미검토 범위를 보고한다. 범위가 지나치게 넓거나 전문 검토가 더 필요하면 조율자가 근거를 기록하고 인원을 추가할 수 있다. 고위험의 별도 테스트 작성·독립 실행 검증·최종 Qwen 코드 리뷰는 유지한다. 시험 결과는 검토 누락·후속 결함·재작업과 이슈당 토큰 사용량을 함께 살펴 평가한다.

기본은 일반·고위험 모두 같은 계획 버전에 독립된 3명이 참여하며 명세형 일반 작업만 1명이다. 위험도 판단과 진행 중 계약 유지 기준은 본문 §3을 따른다. 같은 구현 계열의 critique로 인원 수를 채우지 않는다. 사용 가능한 반대 계열 모델이 부족하면 해당 단계의 제약을 기록하며 자동으로 같은 계열 검토로 낮추지 않는다.

**반대 계열 규칙은 계획 critique에 적용한다. 최종 PR 코드 리뷰는 주야간·위험도·병합 권한과 무관하게 Qwen Code `qwen4-max-preview(openai)`를 사용한다.** 계획·구현·테스트에 참여하지 않은 새 리뷰 전용 세션에서 원격 base/head를 고정한다. 이후 재리뷰는 같은 리뷰 전용 세션을 재사용할 수 있다. Qwen 구현이면 별도 세션이어도 모델 계열이 같음을 기록한다. 모델이 없으면 hold 후 보고한다. 기존 진행 중 작업 계약은 보존한다.

지원되지 않는 추론 수준을 넘기지 않는다. Haiku/Luna의 명확성 점검을 최종 PR 리뷰나 복잡한 안전성 판단으로 대체하지 않는다. 비용·기간 한도가 있으면 배정과 실행 순서에 반영한다.

## 야간 구성

새 위임 시점의 Asia/Seoul 시각이 **23:00 이상 09:00 미만**이면 야간이다. 이 시간은 Qwen·DeepSeek 야간 할인 구간(UTC+8 22:00~08:00)과 같다. 위임마다 시각을 확인하고, 이미 실행 중인 세션은 구간이 바뀌어도 바꾸지 않는다. 시각을 알 수 없으면 주간 구성을 쓴다. 사용자가 명시한 모델은 시각과 무관하게 우선한다.

- **적용:** 일반 작업(명세형 포함)의 구현·수정, TC 작성·검증, 계획 critique, 최종 PR 리뷰. **고위험 구현과 복잡한 원인 분석은 야간에도 주간 모델을 유지하며 최종 리뷰는 Qwen을 사용한다.** 복구하기 어려운 변경을 할인 모델에 맡기지 않기 위한 보수적 기본값이다.
- **하네스:** 모든 Qwen·DeepSeek 세션은 Qwen Code 하네스로 만든다. `traycer_list_harness_models`로 정확한 ID를 확인해 기록한다. 지원되지 않으면 그 사실을 작업 기록에 남기고 최종 리뷰 외 역할만 주간 구성으로 진행한다. 최종 리뷰 모델이 없으면 hold 후 보고하며 몰래 바꾸지 않는다.
- **실제 모델 확인:** 결과 수락과 리뷰 게시 전 transcript의 provider·model을 확인하는 규칙은 같다. 확인할 수 없는 결과는 미검증이다.

## Traycer 세션 생성과 응답

1. `traycer_create_agent`는 **같은 호스트에서 `surface: "gui"`, `routing: "hold"`를 명시**해 호출한다. remote host나 terminal child에 같은 routing 보장이 있다고 가정하지 않는다. 현재 작업에 허용된 프로필을 명시한다. fast mode는 사용자나 가이드 지시가 있을 때만 켜고 권한 모드는 가이드에 별도 지시가 없으면 `full_access`를 사용한다.
2. 생성 후 하네스·모델·프로필·workspace를 확인하고 hold 설정 요청·응답을 기록한다. 조율자가 **결과 수락과 매 리뷰 게시 직전 `traycer_get_transcript`로 해당 결과의 assistant 턴 `provider`·`model`·turn ID를 확인**해 선택한 정확한 모델과 대조한다. 여러 턴의 결과면 기여한 턴들을 확인한다. `traycer_list_agents`는 설정값이므로 실제 실행 모델의 단독 근거가 아니며 보고자의 모델 문자열도 충분하지 않다. 모델이 다르면 해당 결과를 미검증으로 두고 요구 모델에서 다시 수행한다. transcript의 실행 메타데이터를 읽을 수 없으면 출처 확인 대기로 남기며 같은 검토를 맹목 반복하지 않는다. provider-native subagent가 Traycer 설정을 이어받는다고 가정하지 않는다.
3. `traycer_send_message`에 **`expectReply: true`**를 지정해 작업을 전달한다. 새 에이전트 생성만으로 실제 작업이 시작되거나 끝난 것으로 보지 않는다.
4. 배정된 모든 critique는 같은 계획 버전을 받되 서로의 결과에 영향을 받지 않도록 한다. 테스트 작성자와 구현자가 같은 파일을 동시에 수정하지 않게 한다. 리뷰어·실행 검증자는 원격 대상 SHA를 fetch한 별도의 깨끗한 체크아웃을 사용한다.
5. 단계 전환·새 위임 직전과 응답 수락 시 최신 Linear 보류·취소·소유를 재확인한 뒤 작업·시도·실제 모델·SHA·보고를 대조한다. 보류면 로컬 후속 작업과 외부 쓰기를 중단한다. [리뷰 반복·재개 계약](review-loop.md)에 따라 결과를 다음 실제 실행으로 연결한다. 비동기 응답만 남으면 요청의 `expectReply: true`·응답 세션·다음 행동이 기록됐는지 확인하고 polling하거나 대기 턴을 유지하지 않고 현재 진행을 보고한 뒤 응답으로 재개한다.
6. 세션 ID와 시도별 상태를 프로젝트 작업 기록에 보존한다. 완료되고 재사용하지 않을 세션은 활성 작업·셸이 없는지 확인 후 정리한다.

Traycer child에게 구현·TC·검증을 맡길 때 가용한 `traycer-implement`를 적용하도록 한다. 자기 코드를 자신이 독립 검토했다고 보고하지 않게 한다.

## 새 작업의 메시지와 조율

진행 중인 이슈·PR의 기존 보고 계약은 유지한다. 새 작업에서는 아래 위임 항목을 한 번에 전달하고, 긴 원문·로그는 접근 가능한 경로와 필요한 요약으로 연결한다. 계획 critique의 동일 버전·독립성, 검증 원본과 실제 증거는 그대로 제공한다.

결과, 판단이 필요한 차단, 다른 담당자에게 영향을 주는 결정·인터페이스 변경은 바로 알린다. 단순 수신 확인·감사 답장·반복 상태 보고는 기본 생략하거나 결과에 합친다. 응답을 요청받았거나 계약·도구·사용자가 회신을 요구하면 반드시 답하고, 최종 결과와 미검증 사항도 빠뜨리지 않는다. 조율자는 의존성과 다음 담당자를 명시하고 비동기 응답으로 재개하며 불필요하게 재촉하거나 polling하지 않는다. 필수 Slack·PR 보고와 hold·소유·head 확인은 유지한다.

## 토큰·캐시 비용 규칙

- 조율자는 자식 세션에 일을 전달하고 응답이 와야 진행되는 지점에서 턴을 끝낸다. 자식 응답을 기다리며 턴을 열어 두거나 짧은 간격으로 확인하지 않는다. 상태는 대화가 아니라 run manifest·receipt·작업 기록 파일에 두고 재개 때 그 파일에서 읽는다.
- 각 하위 세션에는 역할에 필요한 부분만 전달한다. 스킬·참조 전체나 계약서 전문을 모든 세션에 다시 읽히지 않는다. 역할·모델·SHA·완료 기준·허용 파일·보고 형식과 해당 역할의 규칙 발췌만 준다. 원문·로그는 경로로 연결한다.
- 하위 세션은 계약에 정한 역할만 만든다. 같은 역할의 중복 세션, 요약·진행 감시 전용 세션, 범위 없는 재검토 세션을 추가하지 않는다. 완료되어 재사용하지 않는 세션은 활성 작업이 없는지 확인한 뒤 정리한다.
- 작업 기록에 역할별 모델·추론 수준·세션 ID를 남긴다. 사용량을 읽을 수 있으면 입력·캐시 입력·출력을 역할별로 함께 남겨 다음 등급 조정의 근거로 쓴다. 읽을 수 없는 값은 미확인으로 둔다.

## 매 위임에 전달할 내용

- 역할·모델·추론 수준·허용 프로필·`routing: "hold"`, 현재 승인 범위.
- Linear 원본·계획 버전·저장소·전용 체크아웃·기준 브랜치·검토 SHA.
- 기존 실행 계약의 승인 범위·리뷰 전용 여부·미해결 지적·현재 단계·결과 수신 후 다음 행동. 부모와 child가 서로 상대방의 수정 착수를 기다리지 않게 담당자를 하나로 정한다.
- 수정 가능한 파일·금지 영역·다른 작업자의 범위.
- 완료 기준·관련 TC·실행할 검사·필요한 테스트 코드.
- 결과를 남길 프로젝트 경로·응답 대상·보고 필드. 증거는 삭제 예정 worktree 밖에 보존하고 Slack 발송·worktree 삭제는 조율자만 수행한다.
- 재위임에도 동일한 모델·독립성·TC·증거 규칙 적용.
- 환경변수는 Doppler `jay/shared` 우선 조회 규칙을 전달한다. child에는 키 이름·필요한 제한된 실행 경로·capability만 전달하며 서비스 비밀 전체를 복사하지 않는다.
- **외부 쓰기는 조율자만 담당.** child는 결과를 보고하고 직접 push·Linear/PR/Slack 쓰기나 worktree 삭제를 하지 않는다. 사람이 hold·취소한 경우 후속 작업·외부 쓰기를 중단하는 규칙도 전달한다.

보고는 `역할 / 실제 실행 모델·프로필·시도 식별 근거 / 계획 버전 또는 SHA / 변경·발견 / TC·테스트 경로 / 실행 명령·종료 코드 / 실패·미검증 / 결과 경로`를 포함한다. 조율자는 원자료·실행 메타데이터와 대조하며 보고 문구만으로 통과시키지 않는다.

## 장애와 복구

rate limit·네트워크·하네스 실패는 다음 순서로 처리한다.

1. 해당 시도의 실제 종료·결과·전달 상태를 확인한다. 살아 있는 작업이나 결과가 불명확한 쓰기를 복제하지 않는다.
2. `traycer_list_provider_profiles`와 사용량 조회 등으로 **작업에 이미 허용된 프로필 집합**의 가용성을 확인한다. 집합이 지정되지 않았다면 처음 선택한 프로필만 허용된 것으로 본다. 다른 회사·워크스페이스 연결, 새 유료 계정, 승인된 비용 한도 밖의 프로필은 제외한다.
3. 허용된 다른 프로필이 정상이라면 **처음 선택한 정확한 하네스·모델·추론 수준**을 유지해 새 시도를 구성한다. `routing: "hold"`인 기존 시도도 한도 회복 후 자동 재개될 수 있으므로, 교체 시도를 만들기 전에 기존 시도를 `traycer_stop_agent`로 중지하고 실행·예약·소유 프로세스가 종료됐는지 확인한다. 종료를 확인할 수 없으면 교체하지 않고 대기한다. 기존 시도의 로컬 변경·결과를 보존하고 정본 시도와 세션 ID를 작업 계약에 갱신한 뒤 새 시도도 `routing: "hold"`로 고정한다. 이미 교체된 시도의 뒤늦은 결과는 정본의 검증·리뷰로 수락하지 않는다. 더 오래된 Opus 버전이나 다른 계열로 자동 하향하지 않는다.
   교체 후에는 중지한 시도로 작업 메시지나 재위임을 보내지 않는다. stop·archive도 이후 메시지로 재각성될 수 있으므로 관련 라우팅을 정본 시도로 옮긴다. 폐기한 시도가 다시 실행 중임을 탐지하면 중지하고 같은 작업 공간을 수정하지 못하도록 종료를 확인한다.
4. 허용된 대안이 없으면 해당 단계는 대기로 기록하고 현재 채팅에 이유·재개 조건을 남긴다. 같은 설정을 맹목 반복하거나 한도 회복까지 턴을 붙잡지 않는다. 한도 회복·새 허용 프로필·사용자의 모델 변경 등 실제 조건이 바뀌면 재개한다.

작업 계약에 고정한 구현 계열, 그 반대 계열의 작업 계약에 정한 계획 critique 인원, 최종 코드 리뷰는 지정된 Qwen 모델이라는 제약을 유지한다. 같은 구현 계열의 계획 critique로 대체하지 않는다. 완료되지 않은 검토자를 필수 인원에 포함하지 않는다.
