# 모델과 위임 계약

## 모델 선택과 반대 계열 critique

Traycer agent selection guide를 읽고 `traycer_list_harness_models`로 실제 실행 호스트·작업 디렉터리의 지원 모델·추론 수준을 확인한다. 명시적인 사용자 지시를 우선하고, 역할별 모델 식별자는 최초 배정 시 사용 가능한 같은 계열 최신 모델로 해석해 정확한 식별자를 기록한다.

**계열의 기준은 실제 구현 하네스다.** 사용자 지정 → 기존 작업 계약 → 현재 Codex/Claude 세션 순으로 구현 계열을 정하며 어느 쪽으로도 정할 수 없으면 Codex가 기본값이다. 조율자가 Codex여도 Claude 구현을 지정했으면 Codex 5명이 critique한다. 반대로 Claude 조율자가 Codex 구현을 지정했으면 Claude 5명이 critique한다. 테스트 작성자나 최종 PR 리뷰어 모델로 반대 계열을 계산하지 않는다.

한 이슈마다 `implementation_harness`, `critique_harness`, 계획 작성자·조율자·구현자·검토자의 실제 모델과 세션 ID를 작업 계약에 고정한다. 실행 계획의 기술 내용은 구현 계열의 세션이 작성·보완한다. 조율자 계열이 달라도 계획 작성자와 critique는 반대 계열이 된다. 중간에 구현 계열을 명시적으로 바꾸면 새 구현 계열에서 계획을 보완하고 그 반대 5명이 critique를 다시 수행하며 테스트·검증 배정도 새 구현 계열에 맞춘다. 이전 계획 critique 결과는 이력으로 보존하되 새 조합의 critique로 세지 않는다. 장애 때문에 구현 계열을 몰래 바꾸지 않는다.

| 역할 | Codex 구현 | Claude 구현 | 경계 |
| --- | --- | --- | --- |
| 조율·외부 쓰기 | 현재 작업 소유 조율자 | 현재 작업 소유 조율자 | Codex/Claude 중 단일 담당, 모델 계열은 구현자와 달라도 됨 |
| 실행 계획 작성·구현·리뷰 지적 수정 | Codex Terra · xhigh | Claude Opus · xhigh | 계획 후 critique 결과 반영·로컬 구현·커밋, 외부 쓰기는 조율자 담당 |
| TC·테스트 코드 작성 | 별도 Codex Luna · high | 별도 Claude Sonnet · medium | 구현자와 다른 세션 |
| 독립 테스트 실행·검증 | 또 다른 Codex Luna · high | 또 다른 Claude Sonnet · medium | 최종 코드에서 실제 검사·증거 확인 |

### 계획 critique 5인의 역할

| 관점 | Codex 구현 → Claude critique | Claude 구현 → Codex critique |
| --- | --- | --- |
| 요구사항·범위·완료 기준 | Opus · xhigh | Terra · xhigh |
| 기술 설계·실패 처리·의존성 | Opus · xhigh | Terra · xhigh |
| 재현·테스트·회귀·관측 가능성 | Sonnet · medium | Sol · max |
| 운영·권한·데이터·재시작·되돌림 | Sonnet · medium | Sol · max |
| 명확성·모순·빠진 상태·복잡성 | Haiku · 지원되는 기본값 | Luna · high |

각 행은 독립된 한 명이며 같은 계획 버전에 총 5명이 참여한다. 같은 구현 계열의 critique로 인원 수를 채우지 않는다. 사용 가능한 반대 계열 모델이 부족하면 해당 단계의 제약을 기록하며 자동으로 같은 계열 검토로 낮추지 않는다.

**반대 계열 규칙은 계획 critique에 적용한다. 최종 PR 코드 리뷰는 기존 지시대로 Claude Opus를 유지한다.** Claude Opus가 구현했어도 이 이슈의 계획 작성·critique·구현·테스트·원인 분석에 참여하지 않은 새 Opus 리뷰 전용 세션을 사용한다. 모델 이름뿐 아니라 세션 ID를 대조해 독립성을 확인하고 self-review를 허용하지 않는다. 이후 라운드는 같은 리뷰 전용 세션을 재사용할 수 있다. 구현 계열 변경만으로 기존 Opus PR 리뷰를 무효화하지는 않으며, 원격 base/head·완료 기준·리뷰 범위·독립성이 그대로일 때만 기존 증거를 명시해 재사용한다. 하나라도 바뀌면 새 대상의 Opus 재리뷰가 필요하다. 사용자에게 새 지시가 있으면 그 범위만 변경한다.

지원되지 않는 추론 수준을 넘기지 않는다. Haiku/Luna의 명확성 점검을 최종 PR 리뷰나 복잡한 안전성 판단으로 대체하지 않는다. 비용·기간 한도가 있으면 배정과 실행 순서에 반영한다.

## Traycer 세션 생성과 응답

1. `traycer_create_agent`는 **같은 호스트에서 `surface: "gui"`, `routing: "hold"`를 명시**해 호출한다. remote host나 terminal child에 같은 routing 보장이 있다고 가정하지 않는다. 현재 작업에 허용된 프로필을 명시한다. fast mode는 사용자나 가이드 지시가 있을 때만 켜고 권한 모드는 가이드에 별도 지시가 없으면 `full_access`를 사용한다.
2. 생성 후 하네스·모델·프로필·workspace를 확인하고 hold 설정 요청·응답을 기록한다. 조율자가 **결과 수락과 매 리뷰 게시 직전 `traycer_get_transcript`로 해당 결과의 assistant 턴 `provider`·`model`·turn ID를 확인**해 선택한 정확한 모델과 대조한다. 여러 턴의 결과면 기여한 턴들을 확인한다. `traycer_list_agents`는 설정값이므로 실제 실행 모델의 단독 근거가 아니며 보고자의 모델 문자열도 충분하지 않다. 모델이 다르면 해당 결과를 미검증으로 두고 요구 모델에서 다시 수행한다. transcript의 실행 메타데이터를 읽을 수 없으면 출처 확인 대기로 남기며 같은 검토를 맹목 반복하지 않는다. provider-native subagent가 Traycer 설정을 이어받는다고 가정하지 않는다.
3. `traycer_send_message`에 **`expectReply: true`**를 지정해 작업을 전달한다. 새 에이전트 생성만으로 실제 작업이 시작되거나 끝난 것으로 보지 않는다.
4. 다섯 critique는 같은 계획 버전을 받되 서로의 결과에 영향을 받지 않도록 한다. 테스트 작성자와 구현자가 같은 파일을 동시에 수정하지 않게 한다. 리뷰어·실행 검증자는 원격 대상 SHA를 fetch한 별도의 깨끗한 체크아웃을 사용한다.
5. 단계 전환·새 위임 직전과 응답 수락 시 최신 Linear 보류·취소·소유를 재확인한 뒤 작업·시도·실제 모델·SHA·보고를 대조한다. 보류면 로컬 후속 작업과 외부 쓰기를 중단한다. [리뷰 반복·재개 계약](review-loop.md)에 따라 결과를 다음 실제 실행으로 연결한다. 비동기 응답만 남으면 요청의 `expectReply: true`·응답 세션·다음 행동이 기록됐는지 확인하고 polling하거나 대기 턴을 유지하지 않고 현재 진행을 보고한 뒤 응답으로 재개한다.
6. 세션 ID와 시도별 상태를 프로젝트 작업 기록에 보존한다. 완료되고 재사용하지 않을 세션은 활성 작업·셸이 없는지 확인 후 정리한다.

Traycer child에게 구현·TC·검증을 맡길 때 가용한 `traycer-implement`를 적용하도록 한다. 자기 코드를 자신이 독립 검토했다고 보고하지 않게 한다.

## 매 위임에 전달할 내용

- 역할·모델·추론 수준·허용 프로필·`routing: "hold"`, 현재 승인 범위.
- Linear 원본·계획 버전·저장소·전용 체크아웃·기준 브랜치·검토 SHA.
- 기존 실행 계약의 승인 범위·리뷰 전용 여부·미해결 지적·현재 단계·결과 수신 후 다음 행동. 부모와 child가 서로 상대방의 수정 착수를 기다리지 않게 담당자를 하나로 정한다.
- 수정 가능한 파일·금지 영역·다른 작업자의 범위.
- 완료 기준·관련 TC·실행할 검사·필요한 테스트 코드.
- 결과를 남길 프로젝트 경로·응답 대상·보고 필드. 증거는 삭제 예정 worktree 밖에 보존하고 Slack 발송·worktree 삭제는 조율자만 수행한다.
- 재위임에도 동일한 모델·독립성·TC·증거 규칙 적용.
- 환경변수는 Doppler `jay/shared` 우선 조회 규칙을 전달한다. child에는 키 이름·필요한 제한된 실행 경로·capability만 전달하며 서비스 비밀 전체를 복사하지 않는다.
- **외부 쓰기는 조율자만 담당.** child는 결과를 보고하고 직접 push·Linear/PR/Slack 쓰기나 worktree 삭제를 하지 않는다. 사람이 hold·취소한 경우 후속 작업·외부 쓰기를 중단하는 규칙도 전달한다.

보고는 `역할 / 실제 실행 모델·프로필·시도 식별 근거 / 계획 버전 또는 SHA / 변경·발견 / TC·테스트 경로 / 실행 명령·종료 코드 / 실패·미검증 / 결과 경로`를 포함한다. 조율자는 원자료·실행 메타데이터와 대조하며 보고 문구만으로 통과시키지 않는다.

## 장애와 복구

rate limit·네트워크·하네스 실패는 다음 순서로 처리한다.

1. 해당 시도의 실제 종료·결과·전달 상태를 확인한다. 살아 있는 작업이나 결과가 불명확한 쓰기를 복제하지 않는다.
2. `traycer_list_provider_profiles`와 사용량 조회 등으로 **작업에 이미 허용된 프로필 집합**의 가용성을 확인한다. 집합이 지정되지 않았다면 처음 선택한 프로필만 허용된 것으로 본다. 다른 회사·워크스페이스 연결, 새 유료 계정, 승인된 비용 한도 밖의 프로필은 제외한다.
3. 허용된 다른 프로필이 정상이라면 **처음 선택한 정확한 하네스·모델·추론 수준**을 유지해 새 시도를 구성한다. `routing: "hold"`인 기존 시도도 한도 회복 후 자동 재개될 수 있으므로, 교체 시도를 만들기 전에 기존 시도를 `traycer_stop_agent`로 중지하고 실행·예약·소유 프로세스가 종료됐는지 확인한다. 종료를 확인할 수 없으면 교체하지 않고 대기한다. 기존 시도의 로컬 변경·결과를 보존하고 정본 시도와 세션 ID를 작업 계약에 갱신한 뒤 새 시도도 `routing: "hold"`로 고정한다. 이미 교체된 시도의 뒤늦은 결과는 정본의 검증·리뷰로 수락하지 않는다. 더 오래된 Opus 버전이나 다른 계열로 자동 하향하지 않는다.
   교체 후에는 중지한 시도로 작업 메시지나 재위임을 보내지 않는다. stop·archive도 이후 메시지로 재각성될 수 있으므로 관련 라우팅을 정본 시도로 옮긴다. 폐기한 시도가 다시 실행 중임을 탐지하면 중지하고 같은 작업 공간을 수정하지 못하도록 종료를 확인한다.
4. 허용된 대안이 없으면 해당 단계는 대기로 기록하고 현재 채팅에 이유·재개 조건을 남긴다. 같은 설정을 맹목 반복하거나 한도 회복까지 턴을 붙잡지 않는다. 한도 회복·새 허용 프로필·사용자의 모델 변경 등 실제 조건이 바뀌면 재개한다.

작업 계약에 고정한 구현 계열, 그 반대 계열의 계획 critique 5명, 최종 코드 리뷰는 Opus라는 제약을 유지한다. 같은 구현 계열의 critique로 대체하거나 Codex PR 리뷰를 Opus PR 리뷰라고 바꾸지 않는다. 완료되지 않은 검토자를 5명에 포함하지 않는다.
