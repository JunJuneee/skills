# TC·증거·Linear·PR 기록

## TC와 실행 증거

각 이슈의 AC와 TC를 연결한다. 적합한 unit·integration·E2E를 골라 실제 동작을 검증하며 모든 유형을 기계적으로 추가하지 않는다. 필요한 수동 화면 확인은 추가 증거로 남기고 자동 테스트를 대신하지 않는다.

| TC 필드 | 내용 |
| --- | --- |
| TC ID와 AC ID | 검증할 완료 기준과 연결 |
| 사전 조건 | 데이터·상태·환경 |
| 입력과 행동 | 재현 가능한 단계 |
| 기대 결과 | 관찰 가능한 동작·데이터·오류 |
| 테스트 코드 | 실제 파일·케이스 식별자 |
| 실행 근거 | 검사 대상 SHA, 명령, 시각, 종료 코드, 결과·로그 경로 |

변경과 관련된 정상·오류·경계·회귀·복구를 검증한다. 결함 수정은 가능한 경우 수정 전 실패와 수정 후 통과를 확인한다. 단순 텍스트 일치로 구현을 복사한 검사나 assertion 없는 코드는 유의미한 검증이 아니다.

TC·테스트 코드 작성과 실행 통과는 다르다. 미실행·실패·검증 불가능을 PASS로 쓰지 않는다. 테스트 코드가 없거나 필수 검사를 실행할 수 없으면 검토 완료로 인계하지 않는다. 로컬에서 실행 가능한 검사는 PR 전에 실행하고 PR에서만 실행되는 필수 CI는 PR 생성 후 실제 결과를 확인한다. 이전 실행을 새 SHA의 실행 결과로 표현하지 않으며 프로젝트가 요구하는 최종 head 검사는 해당 head에서 실행한다.

실패하면 격리된 base 체크아웃에서 같은 명령·조건을 비교해 **변경 유발 실패 / 기존 실패 / 환경 문제**를 분류한다. 승인 범위 안의 변경 유발 실패는 수정·재검증한다. 기존 실패는 base/head SHA·출력과 함께 기록하고 무관한 제품 코드를 임의로 고치지 않는다. **기존 실패라도 필수 검사라면 통과 조건에서 자동 제외하지 않는다.** 기존 프로젝트 정책이나 사용자의 명시적 예외가 없으면 해당 필수 검사는 차단으로 남긴다. 비필수 기존 실패는 회귀가 아님을 검증하고 별도 한계로 공개하며 전체 검사 통과라고 표현하지 않는다.

## 프로젝트에 보존할 기록

비밀과 작업 기록은 공용 스킬 저장소 밖에 둔다. 기존 프로젝트 포맷을 재사용하며 새 JSON 스키마나 runner를 의무적으로 만들 필요는 없다.

- 이슈·계정·프로젝트·저장소·기준 브랜치 매핑과 기존 승인 범위.
- claim·작업 소유·시작 시각·단계·시도·세션 ID·worktree·브랜치·마지막 push SHA·PR.
- 계획 버전과 위험도 판정 근거·정해진 인원의 critique 실제 역할·모델·원문 결과, 채택·미채택 근거.
- AC → TC → 테스트 코드 → 검사 명령·SHA·종료 코드·실측과 base 실패 비교.
- 리뷰 라운드·실제 모델 출처·대상 head·발견·수정 SHA·재검증.
- PR 리뷰/댓글 게시 결과·URL, 실제 이슈 상태·원격 head·병합 상태.
- 제이지의 workspace·channel·요청자 user ID·root ts·진행/완료 message ts·실제 delivery 결과.
- 작업 소유 worktree 목록·원격 보존 SHA·프로세스 종료·삭제 확인 또는 정리 대기 사유.

공용 `agent-workflow`나 프로젝트 전용 `run-issue`가 있으면 기존 소유·제품 결정·의존성·작업 계약·완료 증거를 연결한다. 현재 명시적인 사용자 지시가 과거 스킬의 기본 모델·검토 방식보다 우선하며 저장소 보호·필수 검사는 유지한다. 두 절차가 같은 이슈를 각각 선점하지 않게 한다. 과거 검사를 소급 작성하거나 운영 runner 모드를 임의로 바꾸지 않는다.

## Linear 상태와 모든 외부 쓰기의 공통 전제

실제 팀의 상태 ID·이름·의미·보류 라벨을 조회한다. 프로젝트에 review 타입이 있다고 가정하지 않는다.

| 시점 | 상태와 기록 |
| --- | --- |
| 조건 충족·claim 확보 후 실제 착수 | In Progress, 시작 범위·계획/실행 근거 |
| 계획·critique·구현·TC·테스트·PR 리뷰·수정 반복 | In Progress 유지, 필요한 요약·PR 링크 |
| 최종 head 필수 검사·Opus 리뷰·유효 지적 해소 완료 | In Review, 검토 완료 PR·TC·실행 결과·리뷰 링크 |
| 실제 병합과 완료 기준 충족 확인 | 프로젝트 완료 규칙에 따라 Done |
| 의존성·사용자 결정·기술 장애 | 원인·재개 조건, 기존 hold/blocked 수단 |

상위 범위 카드를 하위 이슈보다 먼저 Done으로 처리하지 않는다. PR 생성·응답 수신만으로 In Review/Done으로 전환하지 않는다.

**단계 전환·새 위임 직전·비동기 결과 수락 시점과 push·PR 생성/갱신·리뷰 게시·draft 전환·병합·Linear 갱신·Slack 보고 등 모든 외부 쓰기와 worktree 삭제 직전** 최신 이슈·댓글·사용자 보류·작업 소유를 확인한다. 외부 쓰기는 원격 head도 확인한다. critique 배치·구현·테스트 작성·검증 위임 전에도 검사한다. 조회가 불완전하면 해당 단계 진행·쓰기를 보류한다. 사용자가 Done·취소·hold한 경우 새 위임·후속 구현·외부 쓰기·worktree 삭제를 중단하고 소유 하위 작업도 중지한다. 이미 진행된 요청의 결과만 읽어 확인하고 로컬 기록·현재 채팅에 알린다. hold 중에는 이슈/PR 추가 댓글이나 Slack 진행·완료 멘션도 게시하지 않으며 최신 해제 지시를 확인한 뒤 재개한다.

쓰기 후 재조회해 반영을 확인한다. 실패·타임아웃·부분 조회는 성공이 아니다. 불명확한 쓰기는 실제 이슈·PR·댓글을 먼저 대조하며 다른 API 표면으로 자동 재실행하지 않는다.

최신 권한 있는 사용자 지시로 hold가 명시적으로 부분 해제됐다면 [리뷰 반복과 재개 계약](review-loop.md)의 범위 기록을 따른다. 위 중단 규칙은 현재도 보류 중인 행위에 적용하며, 해제하지 않은 운영·병합·정리 등의 금지를 함께 해제한 것으로 보지 않는다.

## 원격 head 변경과 독립 체크아웃

마지막 리뷰 이후 head가 바뀌면 이전 승인은 최신 승인이 아니다. 작업 기록의 마지막 push SHA·소유 시도와 새 커밋·diff를 비교한다. 작성자 이름/이메일만으로 자기 작업이라고 판단하지 않는다.

- 기록된 지정 구현자의 수정이면 새 원격 head를 검토·재검증한다.
- 외부 커밋이면 범위·현재 소유·사용자 지시를 먼저 읽기 전용으로 확인한다. 승인된 범위 안의 협업 변경이고 소유 충돌이 없으면 보존해 합류·재검증·Opus 리뷰한다.
- 범위 밖·소유 충돌·판별 불가이면 해당 PR의 후속 변경·게시·인계를 멈추고 구체적인 차이와 필요한 결정만 사용자에게 보고한다. 외부 커밋을 임의로 되돌리거나 force push하지 않는다.

리뷰어는 원격 base/head를 fetch한 자기 전용의 깨끗한 체크아웃에서 지정 SHA를 검토한다. 실행 검증자도 검증 대상 커밋으로 고정한 별도 체크아웃을 사용한다. 미커밋 변경이나 오래된 구현자 worktree를 원격 head 근거로 쓰지 않는다.

## PR 리뷰와 CI

조율자가 PR 생성과 모든 외부 쓰기를 맡는다. PR에는 문제와 변경된 동작, 이슈 링크, TC·테스트 코드, 명령·결과·SHA, 제약을 담는다. Opus의 매 리뷰를 PR 자체에 게시한다. 적절하면 줄 단위 리뷰를 쓰며 최소한 PR 리뷰 또는 댓글로 다음을 남긴다.

- 라운드·base/head SHA·실제 리뷰 역할·모델과 확인 근거.
- 검증한 발견: 심각도·파일·위치·발생 조건·영향·수정 제안.
- 지적이 없으면 해당 SHA의 검토 결론.
- 이전 항목별 수정·오탐 사유·미해결 상태와 검사 근거.

조율자가 게시해도 리뷰어의 판단·대상 SHA를 보존한다. 로컬 보고를 게시 완료라고 하지 않으며 게시 응답과 PR 재조회로 확인한다. 수정·push 후에는 새 원격 head의 Opus 재리뷰와 영향받는 테스트를 수행한다. 자동 승인·self-review·지적 숨기기로 종료하지 않는다.

기본은 검토 완료까지 draft 유지다. **저장소 CI 설정에서 필수 체크의 draft 제외 조건과 ready 전환 트리거를 확인·기록한 경우에만** 로컬 필수 검사와 현재 head의 Opus 리뷰를 먼저 통과시킨 뒤 CI 실행 목적으로 draft를 해제한다. workflow 조건·이벤트 설정 또는 관리되는 CI의 권위 있는 설정이 근거다. 체크가 아직 없거나 지연된다는 관측, 임의 대기 시간은 근거가 아니다. 설정을 확인할 수 없으면 draft를 유지하고 CI 설정 확인 대기로 기록한다. 해제했을 때도 검증 대기로 기록하고 Linear를 In Progress로 유지한다. 실제 필수 CI 통과 전에는 검토 완료 인계·병합·Done을 하지 않는다. 실패 후 코드가 바뀌면 수정·검사·Opus 재리뷰한다. draft에서 실행되지 않은 CI를 로컬 검사 통과로 대체하지 않는다.

## 병합·인계

PR 생성까지만 요청했다면 검토 완료 PR을 인계한다. 현재 이슈 범위에서 병합까지 승인했다면 필요한 수정과 독립 리뷰가 끝난 뒤 재승인 없이 병합한다. 다른 PR·저장소·배포까지 범위를 넓히지 않는다.

병합 직전 **최신 Linear 상태·댓글·hold·작업 소유**, 원격 head, Opus 리뷰 대상·실제 모델, 필수 검사와 branch protection을 확인한다. PR 댓글은 Opus 검토 기록이며 GitHub의 필수 승인 리뷰·체크를 대체하지 않는다. 같은 계정의 자기 PR 승인 제한 등으로 필수 승인이 없으면 충족될 때까지 병합하지 않는다. force push·보호 설정 우회로 통과시키지 않는다.

병합 후 실제 병합 SHA와 이슈 완료 기준을 확인하고 Done을 반영한다. 반복 횟수만으로 성공하지 않는다. 실패·자동화 미실행·배포 미확인은 각각 기록하며, 실행 불가 시 장애·남은 항목·재개 조건을 보존한다.

Slack 전달과 worktree 정리는 [제이지 보고·정리 계약](notifications-and-cleanup.md)을 따른다. 이번 run이 직접 완료 기준·병합 결과를 확인하고 기록한 정상 Done 상태에서는 완료 알림·정리를 마무리할 수 있으며, 사용자가 바꾼 Done·취소·hold에는 이 예외를 적용하지 않는다.
