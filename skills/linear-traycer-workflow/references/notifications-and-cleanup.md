# 제이지 Slack 보고와 worktree 정리

## 프로젝트 알림 계약

작업 계약에 다음을 프로젝트의 기존 연결 설정에서 확인해 기록한다. 공용 스킬에는 실제 채널·계정·사용자 ID나 토큰을 넣지 않는다.

- 프로젝트 → Slack workspace·channel ID 매핑.
- 제이지 앱의 bot user/app identity와 허용된 발신 연결·보고 경로.
- 요청자의 확인된 Slack user ID, 작업 identity(이슈·저장소·run), 시작 메시지의 root `ts`.
- 단계별 발송 시도·결과·message `ts`·필요한 permalink·불명확한 쓰기 상태.
- 이번 작업이 생성한 worktree의 정확한 경로·원본 저장소·브랜치·소유 세션.

채널 이름이 비슷하다는 이유로 다른 프로젝트나 회사 워크스페이스에 보내지 않는다. “나”는 인증된 Slack 요청자 또는 프로젝트 계약의 사용자 매핑으로 해석한다. 사용자명·이메일·Traycer handle을 Slack ID라고 추측하지 않으며 `@here`·`@channel`로 대체하지 않는다.

요청이 Slack에서 왔다면 연결 프로그램이 인증·검증한 원본 이벤트의 requester/owner user ID를 사용한다. Traycer 채팅 등 Slack 밖에서 왔다면 현재 요청자와 연결된 기존 온보딩·프로젝트 알림 계약의 **검증된 사용자 매핑**을 찾는다. Composio 사용자 연결로 신원을 확인할 경우에도 그 연결의 소유자가 현재 요청자임을 먼저 확인한다. 봇의 auth 응답에 있는 bot user ID나 여러 명이 든 허용 사용자 목록을 요청자 ID로 간주하지 않는다. 매핑이 없거나 복수 후보라면 필요한 Slack 사용자 식별을 한 번 확인하고 프로젝트 계약에 보존한다. 그 전에는 완료 멘션이 delivery pending임을 분명히 알리며, 멘션이 전송됐다고 보고하지 않는다.

## 제이지 명의와 실제 전송 경로

제이지 환경변수·토큰은 [Doppler `jay/shared` 우선 조회](secrets-and-environment.md)를 따른다. `SLACK_BOT_TOKEN`·`SLACK_APP_TOKEN`을 로컬 `.env`보다 먼저 확인하고 필요한 서비스 프로세스에만 주입한다. 기존 reporting capability를 받은 worker는 토큰을 직접 가져오지 않는다.

조율자가 외부 쓰기를 단일 담당한다. 하위 작업자는 결과를 조율자에게 보고하며 각자 Slack 최상위 글을 만들지 않는다.

1. **제이지 연결 프로그램이 발급한 작업 전용 reporting capability가 있으면 해당 보고 명령을 사용**한다. 전달받은 작업 문맥·capability의 범위만 사용하고 토큰·비밀 파일·DB를 직접 읽거나 임의 수정하지 않는다. 없는 capability나 보고 명령을 만들어내지 않는다.
2. 보고 경로가 시작 글·같은 스레드 답글·실제 사용자 멘션을 지원하는지 실제 계약을 읽어 확인한다. 기존 Slack 요청 스레드와 작업 알림 스레드가 연결돼 있으면 그 매핑을 재사용한다. 분리된 시작 글이 필요한데 연결 프로그램이 지원하지 않으면 임의로 DB 매핑을 넣거나 두 스레드에 중복 보고하지 않는다. 알림 연결 미지원으로 기록한다.
3. 별도 승인된 발신 연결을 사용한다면 **실제로 제이지 bot identity로 인증되는 연결**인지 확인한다. Composio를 쓸 수 있는 터미널에서는 로컬 CLI를 우선하고 알 수 없는 도구는 search·schema로 확인한다. 사용자 OAuth 연결로 보내면서 표시 이름만 제이지로 꾸미지 않는다. 지정 봇을 보장할 수 없으면 다른 사용자·봇으로 자동 대체하지 않는다.
4. 채널·봇·멘션 대상이 불명확하면 기존 설정·인증 문맥에서 먼저 해결한다. 실제로 누락된 매핑만 사용자에게 모아 확인하고, 임의 채널 생성·초대·권한 확대를 하지 않는다.

이 스킬을 편집·설치하는 것만으로 봇·알림 서비스가 설치되거나 Slack 메시지가 전송되지는 않는다. 봇 기능이 미구현이면 필요한 연결 지점을 명시하고 발송 완료라고 보고하지 않는다.

## 최상위 시작 글 하나, 이후 같은 스레드

작업을 실제 선점해 시작할 때, 프로젝트 채널의 **최상위 시작 메시지 한 개**에 짧은 설명과 실제 Linear 이슈 링크를 제이지로 남긴다. 그 메시지의 `ts`를 root로 저장한다. 같은 작업의 시작 글이 이미 있으면 재사용하며 재시작·리뷰 반복으로 최상위 글을 새로 만들지 않는다. 이미 연결된 요청 root가 시작 설명·이슈 링크를 담고 있으면 재사용할 수 있다. 사용자 작성 원문을 봇이 덮어쓰지 않는다.

예시 내용(링크·이슈 번호는 실행 중 실제 값으로 작성):

- 시작: `작업 시작: 이슈 제목 — 무엇을 확인하고 바꿀지 한두 문장. Linear: 실제 이슈 URL`
- 스레드 진행: `계획 교차 검토 완료. 핵심 지적을 반영했고 TC·구현을 진행합니다.`
- 스레드 검증: `회귀 테스트 통과. 현재 PR head를 Opus가 검토 중입니다.`
- 스레드 재수정: `리뷰에서 확인한 오류 경계 조건을 수정했고 관련 검사를 다시 실행합니다.`
- 스레드 완료: `<@확인된사용자ID> PR 작업 완료. 변경 요약 / 실제 PR URL / 테스트·Opus 리뷰 결과 / Linear URL / worktree 정리 결과 / 실제 병합·배포 상태`

실제 Slack payload는 최상위 글에 `thread_ts`를 넣지 않고, 진행·완료 답글에는 저장한 **최상위 root `ts`**를 `thread_ts`로 넣는다. 다른 답글의 `ts`를 root로 쓰지 않는다. `reply_broadcast`는 false로 두며 매 진행 알림을 채널 본문에 다시 띄우지 않는다. 사용자 멘션은 실제 Slack 문법 `<@USER_ID>`를 사용한다.

업데이트는 계획·critique 완료, 구현·TC·검증, PR 생성, 리뷰·수정·재리뷰, 실제 장애·재개 등 **확인된 의미 있는 변화**가 있을 때 보낸다. 고정 주기 heartbeat나 “계속 진행 중”만 반복하지 않는다. 내부 추론·민감한 로그 대신 완료한 일·확인한 결과·다음 단계·실제 대기 원인을 짧게 전달한다. PR이 생기면 진행 스레드에 링크를 넣되 최종 리뷰 전에는 “PR 생성·리뷰 중”으로 표시한다.

완료 메시지는 필수 검사와 최종 Opus 리뷰를 마친 후 **같은 스레드에 PR 링크와 요청자 멘션**을 포함한다. PR까지만 승인된 작업은 “검토 완료 PR, 병합 전”으로 보고하고 Linear Done이라고 쓰지 않는다. 병합도 승인된 작업은 실제 병합 결과와 Done 반영 여부를 구분한다. 정리나 Slack 전달이 미완료이면 그 상태를 별도로 공개하고 전체 전달·정리 완료라고 하지 않는다.

실제 사용자 결정이 필요한 경우에만 같은 스레드에서 요청자를 멘션하고 질문·대안·추천·영향을 정리한다. 계획 후 재승인 단계를 추가하지 않는다. 이미 연결된 봇의 입력·재개 규칙을 따르며 일반 스레드 답글을 임의의 새 승인으로 보지 않는다.

## 전달 확인과 중복 방지

프로젝트·이슈·run·이벤트 단위로 발송 결과를 보존한다. 시작 root와 완료 메시지의 `ts`를 저장하고 실제 채널·root·발신 봇·본문·멘션을 허용된 읽기 경로로 확인한다. **큐 접수는 Slack 전송 완료가 아니다.** 보고 명령이 queue ack만 반환하면 실제 delivery 결과나 Slack 재조회로 확인하며 확인 불가 상태는 pending으로 남긴다.

타임아웃·불명확한 응답 뒤에는 기존 root·메시지와 전송 상태부터 조회한다. 불명확한 시작 글을 재생성하거나 다른 발신 표면으로 자동 재전송하지 않는다. 확정 거절·rate limit은 해당 도구의 재시도 규칙과 Retry-After를 따르되 중복 여부를 먼저 대조한다.

Slack 전송과 worktree 삭제 직전에도 최신 Linear 상태·댓글·사용자 hold·취소·작업 소유를 확인한다. 사용자 hold 중에는 Slack 진행·완료 멘션과 worktree 정리를 중단하고 로컬 기록·현재 Traycer 채팅에 재개 조건을 남긴다. **이번 run이 직접 기록한 정상 Done 전환**과 원격 결과가 일치하면 새 구현 없이 완료 알림·정리만 마무리할 수 있다. 사람이 바꾼 Done·취소·hold에는 이 예외를 적용하지 않는다.

알림 경로 장애는 코드 검증 실패와 구분한다. 이미 승인된 구현·검증은 진행할 수 있지만 전달 대기와 원인을 현재 채팅·로컬 기록에 남긴다. Slack 전송이나 멘션을 확인하기 전 “Slack 알림 완료”로 처리하지 않는다. 사용자에게 알리지 않은 채 봇 계정이나 채널을 변경해 해결하지 않는다.

## PR 작업 완료 후 worktree 정리

사용자가 요청한 자동 정리는 **이번 작업이 만든 임시 worktree만** 대상으로 한다. PR을 처음 만든 직후에는 수정·재검증·Opus 재리뷰에 필요하므로 삭제하지 않는다. PR까지만 맡긴 작업은 최종 검증·리뷰 완료와 원격 push 확인 뒤 정리하며, 병합까지 맡긴 작업은 승인된 병합·충돌 해결·최종 검증을 끝낸 뒤 정리한다. 실패·결정 대기·리뷰 중 작업은 유지한다.

삭제 전 다음을 모두 확인한다.

- 최신 Linear 상태·댓글·작업 소유·사용자 보류를 다시 조회한다. 사람이 바꾼 hold·Done·취소면 보존 조건을 만족해도 삭제를 보류한다. 이번 run이 직접 기록한 정상 Done만 위의 제한된 마무리 예외를 적용한다.
- 작업 기록과 경로·원본 저장소·브랜치·소유가 일치하고, 원본 checkout·사용자 worktree·다른 작업·선행/후속 작업이 필요한 경로가 아니다.
- PR이 실제로 존재하고 최신 작업 commit이 원격 PR branch 또는 병합된 원격 기준 브랜치에 보존돼 있다. 전송 수락·PR 번호만으로 보존을 추정하지 않는다. 원격 head가 달라졌으면 차이·소유·보존을 다시 확인한다.
- tracked/untracked 변경과 submodule 작업이 남지 않았으며, ignored 파일에도 유일한 원자료·필요한 로컬 설정·결과물이 남지 않았는지 확인한다. 로그·TC·리뷰 근거는 삭제 대상 밖의 프로젝트 결과 경로에 보존한다. 복구 가능한 빌드 출력과 유일한 사용자 자료를 구분한다. 비밀값은 로그·공용 스킬로 복사하지 않는다.
- 활동 목록의 `submodules[]` 항목은 teardown이 삭제하는 소유 브랜치다. 각 submodule 저장소·브랜치의 커밋이 자체 원격 branch/PR 또는 병합된 원격 기준 브랜치에 보존됐는지 따로 확인한다. 상위 저장소의 clean/base 상태나 상위 PR 보존만으로 대신하지 않는다. `uncommittedCount`는 dirty submodule도 이미 변경 경로로 세므로 별도 보존 근거로 이중 계산하지 않는다. 확인 불가·미보존이면 정리를 보류한다.
- 해당 worktree를 사용하는 하위 작업·검증 프로세스·서버·셸이 모두 끝났다. 소유 세션은 실행이 끝난 뒤 지원되는 방식으로 archive 또는 유지할 checkout에 재바인딩한다. 다른 작업의 프로세스를 죽이거나 현재 실행 중인 조율자 workspace를 강제로 제거하지 않는다.

Traycer 관리 worktree는 `traycer worktree list --json --include-activity`로 현재 활동·분류를 확인하고 **`traycer worktree delete --path <정확한소유경로>`**로 하나씩 삭제한다. 같은 CLI의 busy check와 teardown을 우회하지 않는다. `in-use`면 삭제하지 않으며 null 상태·오래된 시각·`prState: none`을 안전 근거로 쓰지 않는다. 기존 자동 정리 승인은 위 조건을 만족하는 이 작업의 경로에만 적용하며 host-wide 일괄 삭제로 넓히지 않는다.

`git worktree remove`, `rm -rf`, force 옵션, 임의 DB 삭제로 Traycer 관리를 우회하지 않는다. CLI가 없거나 관리 대상·소유·보존을 증명할 수 없거나 busy/dirty이면 **삭제 대기·이유·대상 경로**를 남긴다. 이 경우에도 검증 완료 PR의 존재와 정리 대기를 구분해 보고한다. 로컬·원격 브랜치와 열린 PR은 삭제하지 않는다. 추후 추가 수정이 필요하면 보존된 원격 branch에서 새 worktree를 만든다.

삭제 뒤 같은 목록을 다시 읽어 경로 제거를 확인하고 `removed / deferred / failed`와 근거를 기록한다. 정상 흐름에서는 정리를 확인한 뒤 Slack 완료 스레드에 PR 링크·사용자 멘션·정리 결과를 보낸다. 삭제 지연·실패를 성공으로 감추거나 Slack 전송 장애 때문에 이미 안전하게 정리한 worktree를 재생성하지 않는다.
