# Linear Traycer Workflow

사용자가 지정하거나 기존 계약으로 승인한 Linear 이슈를 **Slack 시작 보고 → 계획 → 구현 모델의 반대 계열 3인 critique → TC·구현·테스트 → PR → Opus 리뷰·수정·재리뷰 → worktree 정리·Slack 완료 멘션**로 완료한다. 계획 후 승인을 받는 단계를 추가하지 않는다. 조율자가 승인 범위 안의 선택을 판단하고 끝까지 진행한다.

이 스킬은 실행 규약이다. 읽거나 설치했다고 감시 실행기·예약·에이전트가 기동된 것은 아니다. 직접 지정한 이슈는 현재 Traycer 세션에서 처리하며, 주기 감시는 요청된 경우에만 기존 runner에 연결한다. 이슈 구현 요청을 runner 신규 개발로 바꾸지 않는다.

**이 인원 규칙은 새로 시작하는 작업부터 적용한다. 진행 중인 이슈·PR은 기존에 승인된 critique 인원과 작업 계약을 유지하며, 사용자가 해당 작업의 계약 변경을 지시한 경우에만 바꾼다.**

**같은 이슈·PR의 후속 요청에도 기존 작업 계약을 이어받는다.** 이미 수정·검증·재리뷰까지 승인된 작업에서 "리뷰해줘", "확인해줘"라는 짧은 말만으로 리뷰 전용 모드로 바꾸지 않는다. 반대로 기존 실행 승인이 없는 독립 리뷰 요청이나 명시적인 "리뷰만·수정 금지"를 구현·병합 승인으로 확대하지 않는다. [리뷰 반복과 재개 계약](references/review-loop.md)을 읽고 현재 승인 범위·보류 근거·다음 실행을 먼저 확정한다.

현재 작업을 소유한 Codex 또는 Claude 세션 한 명이 조율자다. 구현 모델은 조율자의 모델과 별도로 지정할 수 있으며 **critique 계열은 실제 구현 하네스**를 기준으로 정한다. 기존 조율자가 있으면 그쪽으로 연결하고 진입 세션은 결과만 전달한다. 두 조율자가 claim·push·PR·Linear 쓰기를 중복 수행하지 않는다. 그 외 하네스에서 진입하면 읽기 전용으로 입력을 모아 선택한 구현 계열의 같은 호스트 GUI 조율자 한 명에게 위임한다.

## 1. 대상과 실행 범위를 고정한다

- 최신 Linear 본문·댓글·관계·첨부, 대상 저장소의 `AGENTS.md`, 기준 브랜치, 기존 PR·진행 작업을 확인한다. 프로젝트별 계정·팀·저장소 매핑을 재사용하고 다른 워크스페이스로 대체하지 않는다.
- 프로젝트 전용 실행 절차나 `run-issue`가 있으면 먼저 읽고 기존 claim·담당자·제품 제약·상태 규칙과 연결한다. 현재 사용자 지시가 모델·검토 흐름의 기본값보다 우선하며 저장소의 필수 검사·보호 절차는 유지한다. 같은 이슈에 두 조율자를 중복 실행하지 않는다. 실제 승인 범위가 충돌할 때만 결정을 모은다.
- 이슈의 목표·변경 범위·완료 기준, 기준 브랜치, 필수 검사, PR·리뷰 댓글·병합·배포의 승인 범위를 프로젝트 작업 계약에 남긴다. 기존 대화·계약의 승인은 이어받되 이 스킬 자체로 병합·배포 권한을 만들지 않는다. 승인된 병합을 재확인받을 필요도 없다.
- 독립 이슈마다 worktree·브랜치를 분리한다. 기존 PR·claim이 있으면 해당 작업을 이어가며 중복 구현하지 않는다. 사람의 Done·취소·보류는 존중한다.
- 시작 전 [제이지 Slack 보고·worktree 정리](references/notifications-and-cleanup.md)를 읽고 프로젝트 채널·제이지 발신 경로·요청자 Slack ID·작업 스레드·소유 worktree를 계약에 연결한다. 실제 착수 시 채널 최상위 시작 글에 작업 설명과 Linear 링크를 남기고 이후 진행은 같은 스레드에 기록한다.
- 직접 지시한 이슈의 실행 가능 여부를 확인한다. 감시 실행에서는 기존 ready 상태·라벨·담당자·선행·동시 실행 조건까지 따른다. Backlog 전체를 임의로 승인된 큐로 보지 않는다.
- 필수 정보는 연결된 자료에서 먼저 찾는다. 승인 범위를 넘어서는 제품·데이터·비용 결정이나 실제 권한 부재만 모아 사용자에게 묻는다. 통상적인 구현 선택을 승인 대기로 만들지 않는다.

환경변수·토큰이 필요하면 [Doppler 우선 조회](references/secrets-and-environment.md)를 읽고 **Doppler `jay/shared`를 먼저 확인**한다. 제이지의 `SLACK_BOT_TOKEN`·`SLACK_APP_TOKEN`도 이 경로를 우선한다. 로컬 `.env`가 비었다고 미설정으로 단정하지 않으며 값은 출력·복사하지 않고 필요한 프로세스에만 주입한다. 기존 작업 전용 capability를 받은 child는 서비스 토큰을 직접 가져오지 않는다.

Linear·GitHub·Slack 등 외부 서비스 접근은 [Composio 우선 규칙](../composio-first/SKILL.md)을 따른다. 지정 계정·권한·기능을 충족하는 Composio 연결을 먼저 사용하고 터미널에서는 로컬 CLI를 우선한다. 제이지 봇·작업 capability처럼 지정된 신원과 전용 경로가 있는 작업은 그 계약을 유지한다. 비밀·토큰을 작업 계약이나 공용 스킬에 복사하지 않는다.

## 2. Traycer 역할과 모델을 배정한다

위임 전에 [모델·위임 계약](references/models-and-delegation.md)을 읽는다. Traycer의 agent selection guide와 현재 호스트의 모델 목록을 확인하고 실제 지원되는 모델·추론 수준을 지정한다. **새 작업은 일반·고위험 모두 3명이 실제 구현 하네스의 반대 계열에서 계획 critique**한다. 고위험 3인 체계는 시험 적용하며 다섯 검토 관점을 모두 배정한다. 사용자 지정 → 기존 작업 계약 → 현재 Codex/Claude 세션 순으로 구현 하네스를 선택하고, 어느 쪽으로도 정할 수 없으면 Claude를 기본값으로 쓰며 구현 모델은 Sonnet으로 고정한다. 한 이슈의 구현 계열과 반대 critique 계열을 작업 계약에 고정한다. 테스트 작성·실행은 해당 구현 계열의 별도 세션에 맡기며 **최종 PR 코드 리뷰는 기존 규칙대로 별도 Claude Opus**가 맡는다.

조율자가 Linear·계획·에이전트 결과·PR 상태를 연결하고 외부 쓰기(push·PR 생성/갱신·리뷰 게시·draft 전환·병합·Linear 갱신·제이지 Slack 보고·worktree 삭제)를 단일 담당한다. child는 로컬 구현·검사·리뷰 결과를 보고하며 같은 외부 쓰기를 중복 수행하지 않는다. 재위임에도 같은 계약을 전달한다. Traycer 도구가 없으면 읽기 전용 현황 파악과 재개 기록까지만 수행하고 위임·구현·외부 쓰기는 시작하지 않는다. 축소 실행은 별도 지시가 있을 때만 하며 수행하지 않은 독립 검사를 완료로 표현하지 않는다.

## 3. 위험도에 따라 계획을 독립 critique한다

1. **선택한 구현 계열의 계획 작성 세션**이 목표·대상 코드·완료 기준·제약·검증 방법을 포함한 실행 계획을 만든다. 이 세션은 critique가 끝난 뒤 구현자로 재사용할 수 있다. 사용자 계획이 있으면 유지하며 필요한 부분만 구체화한다. 조율자와 구현 계열이 다를 때도 계획의 기술 내용은 구현 계열에서 작성·보완하므로 작성자와 critique가 반대 계열이 된다. 조율자는 목표·제약을 전달하고 결과를 연결한다.
2. 조율자는 착수 시 작업 내용과 영향 범위로 위험도를 판정하고 근거·인원·역할을 작업 계약에 기록한다. 일반 작업과 고위험 작업 모두 **3명**이다. 데이터 삭제·복구가 어려운 마이그레이션, 인증·권한의 중대한 변경, 결제·금전 처리, 광범위한 아키텍처 변경처럼 실패 영향이 크거나 복구가 어려운 작업은 고위험으로 분류한다. 예시는 자동 분류 규칙이 아니며 실제 영향과 복구 가능성을 기준으로 판단한다. 위험도가 불명확하고 피해가 클 수 있으면 고위험 기준을 적용한다.
3. 구현 계열과 반대인 독립 세션에 같은 계획 버전과 코드 맥락을 전달한다. 일반 작업의 모델·3개 통합 관점과 고위험의 3인에게 배정한 5개 관점은 [모델·위임 계약](references/models-and-delegation.md)을 따른다. 정해진 인원은 총 검토자 수이며 호스트 용량에 맞춰 나눠 실행할 수 있다. 서로의 결론을 읽기 전에 독립 의견을 받는다.
4. 사용 가능한 `traycer-artifact-critique`를 적용하게 한다. 없다면 누락·모순·실패 시나리오·검증 가능성을 실제 코드와 대조하는 검토 계약을 전달하고, 해당 스킬을 실행했다고 주장하지 않는다.
5. 조율자가 근거를 대조해 필요한 지적을 반영한다. 중복을 합치고 채택·미채택 이유를 기록한다. 다수결이나 무조건적인 전부 반영으로 결정하지 않는다.
6. 계획이 실질적으로 바뀌면 확정된 위험도에 해당하는 3명이 바뀐 계획을 다시 검토한다. 구현 계열이 명시적으로 변경돼도 새 계열의 반대 검토자에게 같은 인원의 critique를 다시 받아야 하며 이전 계열의 결과로 대체하지 않는다. 새 규칙으로 시작한 작업을 진행 중 고위험으로 재분류하면 근거를 기록하고 해당 계획 버전에서 3명이 고위험의 다섯 관점을 모두 검토하도록 보강한다. 같은 버전·반대 계열·독립성 조건을 충족한 기존 결과는 포함할 수 있다. 승인된 목표 안에서 정리된 계획은 **사용자에게 재승인받지 않고 구현으로 이어간다**.

계획 critique는 사용자 확인이 필요할 때만 실행하는 조건부 단계가 아니다. 이 워크플로를 적용한 이슈마다 수행한다. 사용자 결정이 실제로 필요한 경우와 자동 critique 실행은 구분한다. 작은 이슈는 계획·위임 맥락·검사 범위를 간결하게 하되 작업 계약에 정한 인원의 critique와 독립성·TC·실행 검증을 임의로 생략하지 않는다.

## 4. TC·테스트 코드·실행 증거를 만든다

[검증·Linear·PR 기록](references/evidence-and-linear.md)의 TC 형식과 상태 전환을 따른다.

- 완료 기준을 관찰 가능한 AC로 만들고 TC를 연결한다. 변경과 관련된 정상·오류·경계·회귀·복구 시나리오를 포함한다.
- 구현자는 지정된 구현 계열로 코드를 변경한다. 해당 계열의 별도 테스트 작성자가 실행 가능한 테스트 코드를 작성하거나 기존 테스트를 보강한다. 테스트 작성은 PR 이후로 미루지 않는다.
- 해당 구현 계열의 또 다른 검증 세션이 최종 커밋에서 관련 테스트와 실행 가능한 필수 로컬 검사를 실제 실행한다. PR에서만 실행되는 필수 CI는 PR 생성 후 확인한다. 구현자의 PASS 보고를 독립 검증으로 대체하지 않는다.
- 실패는 같은 조건의 base와 대조해 변경 유발·선행 실패·환경 문제를 분류한다. 승인 범위 안의 실패만 수정하며 필수 검사 실패는 base에서도 재현돼도 자동 면제하지 않는다. 상세 기준은 검증 참조를 따른다.
- TC 문서만 있거나, 테스트 코드가 실행되지 않았거나, 기대 결과와 다른 경우 통과로 처리하지 않는다. 테스트는 구현 문구를 복제하는 대신 실제 동작·경계를 검증한다.

## 5. PR을 만들고 Opus 리뷰를 반복한다

**단계 전환·새 위임 직전·비동기 결과 수락 시점과 모든 외부 쓰기·worktree 삭제 직전** 최신 이슈·댓글·사용자 보류·작업 소유를 확인한다. 외부 쓰기는 원격 PR head도 확인한다. critique 배치·구현·테스트·검증을 위임하기 전에도 이 검사를 수행한다. 사용자가 Done·취소·명시 hold로 바꾼 것을 탐지하면 새 위임·후속 구현·외부 쓰기·worktree 삭제를 중단하고 소유 하위 작업도 중지한다. hold 중에는 리뷰 게시·draft 해제·worktree 정리도 하지 않는다. 진행 중이던 쓰기는 결과만 읽어 확인하고 로컬 기록·현재 채팅에 재개 조건을 남긴다. 사용자가 보류를 해제한 최신 지시를 확인한 뒤 재개한다. 명시적 부분 해제는 [리뷰 반복과 재개 계약](references/review-loop.md)에 따라 해제된 범위만 재개하고 나머지 금지는 유지한다.

1. 조율자가 검증 결과·Linear 링크·변경 이유·제약을 담은 PR을 만든다. 기본은 draft이며 기존 PR이 있으면 갱신한다. draft에서 필수 CI가 실행되지 않는 저장소는 아래 CI 예외 절차를 따른다.
2. 이 이슈의 계획 작성·critique·구현·테스트·원인 분석에 참여하지 않은 **새 Claude Opus 리뷰 전용 세션**이 원격 base/head를 fetch한 자기 전용의 깨끗한 체크아웃에서 해당 SHA를 고정하고 코드·호출부·완료 기준을 검토한다. 리뷰어의 세션 ID와 정확한 모델을 작업 계약에 고정하며, 이후 재리뷰는 같은 리뷰 전용 세션을 재사용할 수 있다. 구현자의 미커밋 작업 디렉터리를 리뷰 입력으로 쓰지 않는다. 조율자가 결과 수락 시 실제 실행 모델을 transcript의 해당 assistant 턴 메타데이터로 확인한다. `traycer-review`가 있으면 적용하고, 없으면 동일한 독립 코드 검토 범위를 명시한다.
3. **매 라운드 리뷰 결과를 PR 리뷰 또는 댓글로 실제 게시한다.** 지적이 없을 때도 대상 SHA와 결론을 남긴다. 로컬 보고나 Linear 요약만으로 대체하지 않는다.
4. 유효한 지적이 있으면 지정된 구현자가 수정하고 필요한 검사를 재실행한 뒤 조율자가 push한다. 수정 후에는 해당 구현 계열의 독립 검증 세션이 최종 head에서 영향받는 테스트와 필수 검사를 재실행하며, 구현자의 PASS로 대체하지 않는다. 오탐·미채택 지적은 근거를 남기고 Opus가 그 처리를 확인하도록 한다.
5. 새 head를 다시 Opus가 검토한다. **최종 원격 head의 완료 기준 충족·TC/테스트 존재·독립 실행 검증 완료·필수 검사 통과·미해결 유효 지적 없음·리뷰 게시**가 확인될 때까지 수정·검증·재리뷰한다. 비필수 선행 실패는 검증 참조에 따라 회귀 아님을 검증하고 한계로 공개하며, 그 사실만으로 병합을 차단하지 않는다. 라운드 수를 채웠다는 이유로 끝내거나 이전 SHA의 승인으로 새 변경을 통과시키지 않는다.
6. 조건이 충족되면 draft를 해제하고 Linear를 In Review로 전환한다. **CI 예외:** 저장소 CI 설정을 읽어 draft에서 필수 CI가 제외된다는 근거를 확인한 경우에만 로컬 필수 검사와 현재 head의 Opus 리뷰를 먼저 통과시킨 뒤 CI 실행 목적으로 draft를 해제한다. 체크가 아직 없거나 늦다는 관측만으로 예외를 적용하지 않는다. 이때는 검증 대기로 기록하고 Linear를 In Progress로 유지한다. 실제 필수 CI 통과 전에는 검토 완료 인계·병합·Done을 하지 않는다. 실패하면 수정·검사·Opus 재리뷰를 반복한다. 이미 승인된 병합도 최신 Linear 보류·작업 소유·원격 head·필수 체크·저장소 정책을 다시 확인한 후 수행한다. 배포는 별도 승인 범위를 따른다.

요청된 범위 안에서 해결할 수 있는 결함은 계속 수정한다. 권한·인증·사용량·프로세스 장애나 승인 범위를 벗어난 결정 때문에 더 진행할 수 없으면 구체적인 원인·남은 작업·재개 조건을 보존한다. 검사 우회, 타 모델의 Opus 승인 대체, 이 변경의 미해결 유효 결함을 남긴 성공 판정으로 반복을 끝내지 않는다. 프로젝트나 사용자가 정한 예산·기한은 지키되 정해지지 않은 숫자를 승인값으로 만들지 않는다.

**리뷰 결과를 수락한 턴에서 다음 실행까지 연결한다.** 유효한 지적이 있으면 항목별 처분을 기록하고 수정 담당자에게 실제 작업을 전달하거나 승인된 로컬 작업을 시작한다. "수정하겠습니다"라는 답변이나 다음 지시 버튼만 남겨 재승인을 기다리지 않는다. 비동기 대기라면 실제 요청·응답 경로를 기록한 뒤 턴을 끝내고, 결과 도착 시 같은 계약의 다음 단계로 재개한다. 모든 게이트가 통과하면 PR-only는 검토 완료 인계로, 병합 승인 작업은 최신 조건 확인 후 실제 병합으로 이어간다.

## 6. Linear와 실제 결과를 일치시킨다

- **실제 작업 시작:** Todo/ready → In Progress. 계획·critique·구현·테스트·draft PR 리뷰 중에는 진행 상태를 유지한다.
- **최종 검증·Opus 리뷰 완료 PR 인계:** In Review. PR 생성 자체를 검토 완료로 취급하지 않는다.
- **실제 병합과 완료 기준 충족 확인:** 프로젝트 규칙에 따라 Done. 열린 PR이나 리뷰 완료만으로 Done으로 만들지 않는다.
- **대기·장애:** 원인·재개 조건을 이슈에 적고 프로젝트의 기존 hold/blocked 수단을 사용한다. 없는 상태를 만들어 넣지 않는다.

상태 이름과 ID는 실제 팀에서 조회해 매핑한다. 쓰기 전 최신 상태·사용자 보류를 확인하고 쓰기 후 재조회한다. PR·댓글·상태 변경 결과가 불명확하면 대상 상태를 먼저 대조하며 맹목 재시도하지 않는다.

이번 run이 직접 기록한 정상 Done 전환은 원격 결과와 대조한 뒤 새 구현 없이 완료 알림·정리만 마무리할 수 있다. 사람이 바꾼 Done·취소·hold에는 이 예외를 적용하지 않는다.

계획·critique 요약, PR 링크, TC·검사·리뷰 결과, 장애·재개 기록을 Linear에 연결한다. 최종 보고에는 PR·검증 SHA·검사 결과·미해결 사항·실제 병합/배포 상태만 간결히 전달한다. 메시지 전달 수락, 에이전트 생성, 계획 작성은 작업 완료가 아니다.

## 7. Slack 완료 보고와 worktree 정리를 마무리한다

[제이지 Slack 보고·worktree 정리](references/notifications-and-cleanup.md)의 전달·소유·보존 검사를 따른다.

- 시작은 프로젝트 채널의 최상위 글 한 개에 간단한 작업 설명과 Linear 링크를 제이지로 남긴다. 실제로 의미 있는 진행·검증·리뷰·수정 결과는 같은 root의 스레드에 이어 쓴다. 하위 에이전트가 중복 글을 만들지 않는다.
- PR 생성 자체로 worktree를 삭제하지 않는다. 최종 수정·필수 검사·Opus 리뷰와 원격 보존을 확인하고, 승인된 병합까지 끝난 뒤 이번 작업 소유의 임시 worktree만 Traycer CLI로 정리한다. PR까지만 승인됐으면 병합을 기다리지 않고 검토 완료 PR의 원격 보존 확인 후 정리한다.
- 최종 스레드 답글에는 실제 PR 링크, 검증·리뷰·병합 상태, worktree 정리 결과와 **요청자의 실제 Slack 멘션**을 넣는다. 제이지 봇 대신 사용자 계정으로 보내거나 일반 @이름으로 알림을 대체하지 않는다.
- 봇 큐 접수·실제 Slack 전송·코드 작업 완료·worktree 정리는 별개로 기록한다. 정리·알림이 대기이면 그 이유를 공개하고 완료로 꾸미지 않는다.
