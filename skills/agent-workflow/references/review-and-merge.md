# 검토와 병합

## 독립 검토

PR 번호·저장소·head SHA/tree·실제 base를 먼저 고정한다. 작성자가 본인의 PASS만으로 최종 검토를 대체하지 않는다. 모델별 역할보다 작성자와 다른 시각으로 실제 코드·호출부·회귀를 확인하는 것이 중요하다. 새 에이전트가 필요하다면 환경의 모델·권한 선택 규칙을 따른다.

검토자는 발견을 실제 코드와 temp/mock 반례로 확인하고 우선순위·원인·영향을 남긴다. 필요한 변경을 결정에 도움이 되게 적는다. 기존 전체 검증이 충분하면 중복 all 실행을 기본으로 요구하지 않는다.

여러 PR은 각각 파일 충돌이 없어도 **합류 코드에서** 검토·검증한다. 예: Provider 언어와 상태 라벨 덮어쓰기, 스키마 필드 누락, 같은 함수의 의미 변경. 디자인 원본 무수정 조건은 immutable upstream의 바이트와 대조한다. 어댑터를 보정했다고 vendor 원본까지 임의로 포크하지 않는다.

초기 상태뿐 아니라 중요한 runtime 전환도 검사한다. 동작 줄이기의 초기 정지만 확인하면 페이지가 열린 뒤 설정을 켜거나 끄는 결함을 놓칠 수 있다. viewport 확인과 실기기 키보드 확인은 별도 근거다.

## 충돌 해결과 최종 대상

격리 worktree에서 최종 합류 후보를 만든다. 각 변경이 보장한 동작을 동시에 유지하도록 충돌을 해결하고 해당 코드를 다시 검토한다. 수정한 최종 SHA/tree와 테스트 근거를 연결한다.

변경 영향에 맞게 검증한다. 프런트 수정 후 frontend·e2e만 재실행하고 기존 unit/crawler 근거를 재사용했다면 각각 어느 SHA에서 실행했는지 밝힌다. 이를 최종 SHA의 `all rc=0`으로 표현하지 않는다. 프로젝트가 최종 all을 요구하면 그 계약대로 실행한다.

## 승인된 PR 병합

사용자가 특정 PR의 검토·수정·검증·병합을 요청했다면 그 범위는 재승인 없이 마무리한다. 다른 PR이나 배포까지 포함하지 않는다.

병합 직전에 원격 head와 검사 대상이 같은지 확인한다. 기존 head를 보존하는 normal push·merge를 우선하며 repository hook·정책을 존중한다. force push나 설정 우회가 필요하다고 자동 가정하지 않는다. head가 달라지면 추가 변경을 확인한다.

여러 PR은 의존 순서로 병합하고 실제 main tree가 검증한 후보와 일치하는지 확인한다. main이 동시에 변경됐거나 결과 tree가 다르면 새 실제 코드를 검증한다. GitHub 체크가 없다면 “CI 통과”를 만들어 쓰지 않고 로컬 명령·결과를 적는다.

선행 일부만 병합됐을 때 후속 작업이 너무 일찍 시작할 수 있다. 그 경우 계약이 허용하는 기존 hold 수단으로 후속만 잠시 보류하고 변경 전 상태·소유를 기록한다. 병합이 끝나면 **이번 작업이 추가한 보류만** 해제한다. 기존·새 사용자 hold는 보존한다. 중간 실패 시 보류와 실패 지점을 남기고 필요한 수정을 계속한다.

완료 상태는 실제 병합 사실과 프로젝트 규칙에 따라 갱신한다. In Review의 의미를 Done으로 바꾸는 방식으로 선행 대기를 없애지 않는다. 후속의 시작은 state·실제 프로세스·로그로 확인하며, lane 점유 때문에 큐에 있는 경우를 실행 중으로 보고하지 않는다.

## 검증된 선행에서 스택 시작

runner가 스택을 지원하고 그 운영 변경이 승인됐을 때만 적용한다. 문서에 계획이 있다는 이유로 기존 main 기반 runner가 스택으로 실행 중이라고 주장하지 않는다.

시작 조건은 열린 선행 PR, 검증한 현재 head, 합류 가능한 상태다. `parents=[{issue, branch, sha}]` 같은 부모 기록을 job·PR에 남기며 검증된 SHA에서 갈라진다. 합류 코드에서 후속 검증을 수행한다.

작은 v1에서는 **아직 완료되지 않은 선행이 하나 이하**일 때만 시작할 수 있다. 이미 완료됐다고 표시된 다른 선행이 실제 기준 브랜치에 포함됐는지도 확인한다. 여러 미완료 선행을 임의로 생략하지 않는다. 다중 합류 ref 검증을 구현하지 않았다면 대기한다.

부모 head가 바뀌면 자식 증거를 stale로 표시하고 새 부모를 합류·재검증한다. 충돌·검사 실패는 자동 성공으로 넘기지 않는다. 부모가 병합 없이 닫힘·취소·결정 변경이면 후속을 hold하고 필요하면 PR을 draft로 둔다. 자동 merge는 별도 승인 범위다.

부모 병합 후 PR base는 실제 API로 재지정하고 값을 다시 읽는다. 브랜치를 남기는 저장소에서 GitHub가 자동으로 main을 잡는다고 가정하지 않는다.
