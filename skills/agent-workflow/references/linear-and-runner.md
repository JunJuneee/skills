# Linear와 자동 실행

## 기존 규칙을 먼저 읽는다

API 접근 방법, 프로젝트·팀 ID, 상태·라벨, runner의 선택 조건과 의존성 처리를 확인한다. 상태 이름만 보고 일을 집지 않는다. title·본문·역할 라벨·lane·선행 카드가 실행 조건에 쓰일 수 있다. 보기 편하게 만들기 위해 실행 조건을 바꾸지 않는다.

카드는 승인된 목표 안에서 만들거나 갱신한다. 이미 완료된 카드를 새 디자인 원본 발견만으로 다시 열지 않는다. 먼저 immutable 원본과 현재 파일의 실제 버전·바이트를 비교한다.

카드 생성이 API 한도에 막히면 실제 거절 사유를 남긴다. 기존 카드를 무단 삭제·보관하거나 유료 플랜을 구매하지 않는다. 권한 범위의 로컬 카드·격리 구현을 계속할 수 있지만, 그 카드를 Linear runner가 자동으로 선택한다고 보고하지 않는다.

## 사용자 결정은 한곳에 모은다

프로젝트의 결정 라벨로 필터한 보기에는 아직 결정이 필요한 카드만 넣는다. 각 카드에는 결정할 질문, 선택지, 실제 확인한 사실·출력·기준 시각, 범위·비용 영향을 적는다. 승인된 목표 안의 통상적인 작업 분해는 결정 라벨로 막지 않는다.

프로젝트가 별도 규칙을 정하지 않았다면 다음 방식을 제안한다.

1. 사용자는 카드 댓글에 선택과 조건을 적는다.
2. 선택이 완료됐을 때 결정 대기 라벨을 제거한다. 기존 상태를 임의로 Done으로 바꾸지 않는다.
3. 에이전트는 최신 댓글과 라벨을 다시 조회한다. pagination과 정렬을 확인해 오래된 댓글을 최신 답변으로 오인하지 않는다.
4. 결정이 기존 승인 범위에 들어가는지 확인하고 작업 계약·실행 입력에 반영한다. 라벨 제거만으로 새로운 비용·수집·보관 정책까지 승인된 것으로 보지 않는다.
5. 선행·lane·동시 실행 조건이 충족되면 시작한다. 충족되지 않으면 구체적인 대기 원인을 남긴다.

라벨 명칭과 의미는 프로젝트에서 읽어 매핑한다. 이미 있는 `needs-confirm`, `agent-hold`, `blocked` 등이 있다면 각각 결정·명시 보류·실패를 섞지 않는다.

## 단계별 열 × 기능별 행 보드

기존 이슈 상태를 유지하고 별도 단일 선택 분류 그룹으로 “단계”와 “기능”을 표현한다. 상태를 개발 단계로 대체하지 않는다. 보드 필터·그룹 설정·분류 라벨이 runner 선택 조건과 충돌하는지 확인한다.

API의 이슈 수와 native 화면의 카드 표시를 따로 검증한다. 공유 목록에 보드가 포함되는지, 팀·프로젝트 스코프와 클라이언트 필터·보관·하위 이슈 표시를 확인한다. API가 이슈를 반환했다는 이유로 사용자의 빈 화면이 해결됐다고 선언하지 않는다.

## 백그라운드 실행 확인

확인은 다음 연결로 한다.

- 스케줄러·runner 프로세스가 살아 있는지와 pause·usage 보류 여부.
- state의 active job, lane, 시작 시각, PID·명령 식별 정보.
- 실제 프로세스 생존과 해당 job 로그의 최근 진행·종료·검증 상태.
- 후보 카드가 선택되지 않은 이유: 사용자 결정, 선행 미완료, lane 점유, 용량, 보류 등.

이슈가 In Progress라는 사실만으로 프로세스 실행을 단정하지 않는다. runner가 살아 있지만 실행할 후보가 없는 상태도 정상적으로 구분한다.

추가 완료 검사가 runner 감시를 멈추지 않도록 한다. 검증은 Popen/poll 또는 환경의 동등한 비차단 작업으로 시작하고 tick마다 기존 세션 종료·정체·시간 상한 감시와 함께 확인한다. 작업 SHA·시작/deadline·고유 attempt 경로·PID 식별을 저장하며 재시작 시 validating 작업을 지우지 않는다.

검증 동시 수·검증 중 새 작업 선택 여부는 계약에서 정한다. 작은 운영의 예시는 “검증 1건, 검증 중 새 세션 시작 보류”다. 종료 코드 복구 불가·PID 재사용·spawn 기록 전 종료를 성공으로 간주하지 않는다. 고유 attempt로 기존 프로세스를 찾고 소유한 프로세스 그룹의 자식까지 종료된 뒤 슬롯을 정리한다. 포트나 PID 숫자만 보고 다른 서버를 죽이지 않는다.
