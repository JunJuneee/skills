# Agent Workflow

사용자가 승인한 목표를 실제 작업물까지 연결한다. Claude·Codex 등 특정 모델이나 Traycer에 종속되지 않는다. 스킬은 작업 규약이며, 백그라운드 실행기는 프로젝트의 기존 runner·CI·스케줄러를 사용한다. 이 문서를 만들거나 읽었다는 이유로 자동 실행이 설치·기동됐다고 보고하지 않는다.

## 승인 범위부터 고정

대화의 가장 최근 지시와 앞서 승인된 범위를 함께 읽는다. 목표, 변경할 동작, 대상 저장소·브랜치, 완료 기준, 금지 사항, 합의된 비용·작업 수 상한을 작업 계약에 기록한다. [작업 계약 템플릿](assets/work-contract.md)을 프로젝트에 맞게 채운다. 알 수 없는 한도를 승인된 숫자로 만들어 넣지 않는다.

- 이미 승인된 목표 안의 작업 분해, 재현된 결함 수정, 격리 작업, 검증은 진행한다. 에픽마다 재승인을 요구하지 않는다.
- 새 제품 동작·정책, 데이터 수집·보관 변경, 비용·범위 확대처럼 실제 선택이 필요한 경계만 사용자에게 모은다. 사실 확인과 구현 선택을 사용자 결정으로 떠넘기지 않는다.
- PR 작성, 병합, 배포, 외부 공개의 승인은 각각 현재 지시에서 확인한다. “PR을 만들어줘”를 병합·배포 승인으로 확대하지 않는다. “검토 후 병합해줘”는 수정·검증 후 해당 PR을 병합하라는 승인이다.
- 사용자가 정한 비용 예외·기한을 따른다. 이 스킬이 사용량 한도나 보호 설정을 임의로 바꾸지 않는다.

작은 작업은 계약과 산출물을 간단히 남긴다. 기존 규약이 있으면 새 상태 체계나 runner를 먼저 만드는 대신 그 규약과 연결한다.

## 필요한 절차만 읽기

| 지금 하는 일 | 읽을 문서 |
| --- | --- |
| 작업 카드·의존성·사용자 결정·실행 여부 확인 | [Linear와 자동 실행](references/linear-and-runner.md) |
| 사실 확인·역할 보고·독립 검사·완료 판정 | [완료 증거](references/completion-evidence.md) |
| 정적 결과 페이지·근거 복사·게시·미리보기 | [결과물 전달](references/delivery-and-preview.md) |
| 코드 검토·충돌 해결·선행 브랜치·병합 | [검토와 병합](references/review-and-merge.md) |

가용한 저장소 도구, API, 브라우저, 에이전트 도구를 사용한다. 이름이 같은 스킬이나 특정 MCP가 설치되어 있다고 가정하지 않는다. 도구가 없으면 가능한 범위를 수행하고 남은 제약을 명시한다. 승인된 API 키는 기존 비밀 저장 경로에서 사용하고 값 자체를 출력하거나 커밋하지 않는다.

## 작업에서 결과까지

1. **현황 확인**: 저장소·원격 head, 카드 상태·의존성, runner 설정·활성 job을 실측한다. 기존 이슈와 작업물을 재사용하며 관련 없는 변경을 보존한다.
2. **작업 분해**: 완료 기준을 관찰할 수 있는 동작·데이터·명령으로 적는다. 필요한 카드만 생성한다. 데이터 판단에는 실제 읽기 전용 쿼리, 원본 출력, 수치, 데이터 기준 시각을 붙인다.
3. **실행**: 작업별 격리 worktree에서 구현한다. 사용자가 요청한 구현을 계획 제출만으로 끝내지 않는다. 독립적인 일은 병렬로 진행하고 같은 파일을 동시에 수정하게 하지 않는다. 위임할 때는 [에이전트 작업 지시 템플릿](assets/agent-brief.md)으로 역할·변경 범위·제출 대상·근거 경로를 전달한다.
4. **검토·검증**: 의미 있는 코드 변경은 작성자와 다른 검토자가 실제 최종 변경을 읽는다. 테스트는 동작과 경계 조건을 확인하며 구현 문구만 복제하는 검사는 피한다.
5. **완료 증거**: 이슈가 In Review이거나 세션이 “PASS”라고 말한 사실만으로 검증 성공을 선언하지 않는다. 실제 제출 SHA/tree, 역할별 완료 보고, 검사 종료 코드, 완료 기준별 실측을 연결한다.
6. **전달**: 별도 요약 LLM을 기본으로 추가하지 않는다. 보존된 보고·검사·스크린샷을 결정적 후처리로 묶고 사용자가 열어 볼 경로를 남긴다.
7. **후속 실행**: 병합 승인 범위라면 검토·충돌 수정·검증 후 병합한다. 선행 완료가 자동 실행 조건을 충족하는지 확인한다. 큐에 들어간 상태와 프로세스가 시작된 상태를 구분한다.

## 기존 운영에 새 검사를 도입할 때

새 완료·전달 게이트는 기본 **observe**로 시험한다. 기존 운영이 enforce라면 모드를 무조건 낮추지 않는다. 현재 모드와 도입할 기능을 구분하고 사용자의 지시를 따른다.

observe에서는 기존 판정을 유지하면서 새 증거·결과물을 기록한다. 검사 실패를 이유로 기존 상태를 되돌리거나 blocked를 새로 붙이지 않는다. 검증 대기 중 사람이 Done·hold·완료 기준을 바꿨다면 그 변경을 보존한다. 외부 코멘트 게시도 별도 허용이 없는 observe에서는 하지 않는다.

운영 전환은 단계별로 확인한다.

| 단계 | 완료라고 말할 수 있는 것 |
| --- | --- |
| 완료 증거 수집 | 특정 SHA의 독립 검사·기준별 근거 확보 |
| 결과물 묶음 | 자체 포함된 결과 페이지 생성·링크 확인 |
| 외부 전달 | 허용된 위치에 게시하고 반환값으로 확인 |
| 미리보기 | 지정 코드의 준비·기동·상태 확인 |

observe 시범 1건은 가능하면 새 규약으로 시작한 이슈를 선택한다. 구형 세션의 보고 계약이 없으면 부족한 증거를 그대로 기록하고, 성공을 맞추기 위해 로그나 판정을 소급 작성하지 않는다.

## 보고

사용자에게 작업물 경로, 검증 대상 SHA와 시각, 통과·실패·확인하지 못한 기준, PR·병합·배포의 실제 상태, 필요한 결정만 전달한다. 백그라운드 진행은 현재 job과 로그로 확인한다. 알려진 결함이나 검증 공백이 있으면 “전체 완료”로 뭉뚱그리지 않는다.

지속되어야 할 결정은 프로젝트 문서나 작업 계약에 남긴다. Traycer를 쓰는 환경에서는 artifact를 사용할 수 있지만, 이 스킬의 공용 저장소에는 개인 경로, 실제 이슈 기록, API 키, 세션 로그, DB를 가져오지 않는다.
